# 第 13 天：英文与零散高频考点集中清理

## 一、今天的目标

第 13 天不是去啃一整块新的项目管理过程，而是专门处理信息系统项目管理师备考里最容易被忽视、却又最容易在综合知识里稳定丢分的一类内容：英文题和零散高频考点。

这一模块的特点非常典型：

- 综合知识里的英文题通常不追求特别深的技术阅读能力，但会考你是否认得常见项目管理术语、是否能读懂简单项目场景和管理指令。
- 零散高频考点分布很散，常见于职业道德、标准规范、组织级资产、事业环境因素、PMO、项目群、项目组合、组织结构、知识产权和合规边界等内容。
- 这些题单独看都不难，但因为分布零碎、容易轻敌，所以经常成为“本来能拿到、最后没拿到”的失分点。
- 论文虽然主要用中文写作，但项目背景中常常会出现英文缩写、系统模块英文名、组织角色英文表达。如果平时完全不整理，到了后期会出现术语混乱、缩写乱写、模块名称不统一的问题。

完成今天后，你至少要达到以下状态：

- 高频项目管理英文术语不再陌生。
- 能读懂一段简单的项目邮件、会议通知或问题升级说明。
- 能区分 issue、risk、deliverable、milestone、baseline、change request 这类高频英文词。
- 能掌握职业道德、标准规范、知识产权、组织级资产、事业环境因素等零散高频点。
- 能把 day1 主项目背景中的系统模块、组织结构和常见缩写补齐成一份统一表达表。

今天的最低交付物有 4 项：

## 三、今天必须先了解的信息

### 1. 为什么 day13 不是“可有可无”的一天

很多考生会把英文题和零散知识自动归类为：

- 分值不高
- 范围太散
- 临场蒙一蒙也行

这是一个典型误区。

因为这部分的特点恰恰是：

- 难度通常没有案例题和论文高
- 但丢分非常稳定
- 一旦你提前系统整理过，反而是最容易快速提分的一块

day13 的本质不是深挖某个大专题，而是把之前容易漏掉的分数尽量收回来。

### 2. 英文题通常怎么考

信息系统项目管理师里的英文题，通常不会考长篇技术论文阅读，更常见的是：

- 项目管理高频术语识别
- 简短项目邮件、通知、会议记录理解
- 英文缩写辨析
- 英文场景下的项目管理动作判断

所以你不需要把目标定成“英语特别强”，而是要做到：

**见到常见术语和常见项目句式时，不慌、不陌生、能判断。**

### 3. 零散高频考点为什么总让人丢分

这类题的共性是：

- 概念不难
- 但边界很容易混
- 平时没系统整理，就会在选项里犹豫

例如：

- issue 和 risk 的区别
- OPA 和 EEF 的区别
- standard、guideline、law 的约束强度不同
- 项目、项目群、项目组合、PMO 的边界不同
- 职业道德题里“人情处理”和“合规底线”不能混

### 4. 今天和前几天的关系

- day4 到 day12 已经把项目管理主干模块系统过了一遍。
- day13 则是专门做一次“查漏补缺”和“边角收口”。

也就是说，今天的任务不是建立新主线，而是把之前容易零散掉的知识重新整理成可记忆、可提分的结构。

### 5. 今天真正要完成的 5 件事

1. 建立英文题和零散题的清理框架。

## 四、今天要掌握的核心知识

## 1. 英文题的本质不是“翻译”，而是“识别关键词”

今天必须先建立一个判断：

- 英文题很多时候不要求你把每个单词都翻得很漂亮
- 更重要的是识别出关键词，再映射到项目管理概念

例如：

- issue 通常对应“问题”
- risk 通常对应“风险”
- stakeholder 通常对应“干系人”
- milestone 通常对应“里程碑”
- acceptance criteria 通常对应“验收标准或验收条件”

### 1. 做英文题时最优先抓什么

优先抓下面 4 类词：

1. 名词：项目管理对象是什么。
2. 动词：正在发生什么动作。
3. 限定词：must、should、before、after、cannot、only。
4. 结果词：delay、approve、accept、mitigate、escalate、review。

### 2. 英文题最容易犯的错

- 逐词死翻，结果忘了题目到底在问什么。
- 只看熟词，不看管理含义。
- 看见英文就慌，其实句子结构很简单。

## 2. 高频项目管理英文术语

下面这些词是 day13 必须熟到“见词有反应”的：

| 英文术语 | 常见中文含义 | 高频考法 |
| --- | --- | --- |
| project charter | 项目章程 | 正式授权项目、授权项目经理 |
| deliverable | 可交付成果 | 阶段性交付物或最终成果 |
| milestone | 里程碑 | 关键时间节点，不强调持续工作量 |
| stakeholder | 干系人 | 受项目影响或能影响项目的人或组织 |
| issue | 问题 | 已经发生并需要处理的事项 |
| risk | 风险 | 尚未发生但可能影响目标的不确定事件 |
| baseline | 基线 | 经确认后作为依据的受控版本 |
| change request | 变更请求 | 对范围、进度、成本、文档等调整的正式请求 |
| acceptance criteria | 验收标准 | 被接受前必须满足的条件 |
| procurement | 采购 | 从外部获取产品、服务或成果 |
| statement of work | 工作说明书 | 采购中对工作范围和交付要求的说明 |
| lessons learned | 经验教训 | 可复用的项目知识沉淀 |
| escalation | 升级上报 | 按机制向更高层推动决策或处理 |
| corrective action | 纠正措施 | 对已偏离情况进行纠偏 |
| preventive action | 预防措施 | 事前降低风险或偏差发生概率 |
| resource leveling | 资源平衡 | 为解决资源过载而调整进度，可能影响关键路径 |
| resource smoothing | 资源平滑 | 不突破主要时间约束下优化资源分布 |
| work performance report | 工作绩效报告 | 对绩效信息进行整理分析后的正式输出 |
| work breakdown structure | 工作分解结构 | 对项目范围进行层次分解 |
| integrated change control | 整体变更控制 | 统一评估、审批和管理变更 |

## 3. 高频英文缩写

这部分很适合做成小卡片反复看。

| 缩写 | 英文全称 | 常见中文含义 |
| --- | --- | --- |
| WBS | Work Breakdown Structure | 工作分解结构 |
| SOW | Statement of Work | 工作说明书 |
| PMO | Project Management Office | 项目管理办公室 |
| CCB | Change Control Board | 变更控制委员会 |
| KPI | Key Performance Indicator | 关键绩效指标 |
| SLA | Service Level Agreement | 服务级别协议 |
| UAT | User Acceptance Test | 用户验收测试 |
| API | Application Programming Interface | 应用程序接口 |
| EVM | Earned Value Management | 挣值管理 |
| CPI | Cost Performance Index | 成本绩效指数 |
| SPI | Schedule Performance Index | 进度绩效指数 |
| OPA | Organizational Process Assets | 组织过程资产 |
| EEF | Enterprise Environmental Factors | 事业环境因素 |
| RAID | Risks, Assumptions, Issues, Dependencies | 风险、假设、问题、依赖清单 |
| RACI | Responsible, Accountable, Consulted, Informed | 责任分配矩阵 |

### 1. 高频缩写易错点

- 不要把 OPA 和 EEF 混了。
- 不要把 CPI、SPI 这种指标缩写看成“背下来就行”，要知道它们和成本、进度绩效有关。
- 不要把 CCB 和 PMO 混成同一类组织对象，一个偏变更决策，一个偏组织级项目支持与治理。

## 4. 英文题的快速阅读方法

### 1. 三步法

看到英文题时，优先做这三步：

1. 先看题干到底问什么。
2. 再抓场景里的核心名词和动词。
3. 最后把英文映射回熟悉的项目管理概念。

### 2. 常见高频句式

以下表达经常出现：

- submit the report：提交报告
- obtain approval：获得批准
- meet the acceptance criteria：满足验收标准
- mitigate the risk：减轻风险
- escalate the issue：升级问题
- allocate resources：分配资源
- revise the schedule：修订进度计划
- maintain the baseline：维护基线
- conduct a review：开展评审
- disclose sensitive data：披露敏感数据

### 3. 看到这些词要立刻警觉

- before / after：时间先后
- must / shall：强约束
- may / might：可能性
- unauthorized：未授权
- unresolved：尚未解决
- final acceptance：最终验收

## 5. 职业道德高频边界

职业道德在考试里经常不难，但很会“挖坑”。

### 1. 必须守住的底线

- 如实汇报
- 公平公正
- 保守秘密
- 尊重知识产权
- 避免利益冲突
- 不伪造、不隐瞒、不误导

### 2. 常见场景陷阱

- 供应商送礼、请客、安排私人旅行
- 为了赶进度隐瞒缺陷
- 复用无授权软件或文档
- 共享敏感数据给无关人员
- 采购评审中带入私人关系

### 3. 快速判断法

如果一个选项看起来“人情上好像说得过去”，但破坏了：

- 公平
- 诚信
- 保密
- 合规

那它大概率就不是正确答案。

## 6. 标准、规范、流程、指南的边界

这部分是典型零散高频考点。

| 概念 | 重点理解 |
| --- | --- |
| law / regulation | 法律法规，强制性最高 |
| standard | 标准，强调统一性和规范性 |
| specification | 规范、规格说明，更偏具体要求 |
| procedure / process | 流程、程序，强调步骤和执行顺序 |
| guideline | 指南，更多是推荐性和参考性 |
| baseline | 基线，强调经确认后受控 |

### 1. 高频判断点

- 法律法规通常不能随意违反。
- 标准和规范往往用于统一要求和判断依据。
- 指南不等于没有价值，但约束性通常弱于法规和正式标准。
- 流程强调怎么做，基线强调按哪个版本做。

## 7. OPA 与 EEF

这组概念几乎年年都容易混。

### 1. OPA 是什么

OPA 强调的是组织内部沉淀下来的可复用资产，例如：

- 模板
- 历史项目文档
- 经验教训库
- 政策和流程文件
- 风险分类表
- 检查清单

### 2. EEF 是什么

EEF 强调的是项目团队通常不能轻易改变、但会影响项目的环境条件，例如：

- 组织文化
- 市场环境
- 法规环境
- 基础设施条件
- 行业竞争情况
- 组织结构

### 3. 快速区分法

- 组织留下来的“可拿来用”的东西，更像 OPA。
- 外部或组织环境里“会影响你、但不一定由你决定”的，更像 EEF。

## 8. PMO、项目、项目群、项目组合

### 1. 项目

强调：

- 临时性
- 独特成果

### 2. 项目群 Program

强调：

- 一组相互关联的项目
- 通过协同管理获取单独管理时拿不到的整体收益

### 3. 项目组合 Portfolio

强调：

- 从组织战略角度进行项目和项目群的组合管理
- 重点不一定是项目彼此关联，而是资源配置和战略优先级

### 4. PMO

强调：

- 提供标准化方法、治理支持、模板、监督和协调
- 不等于替代所有项目经理做执行工作

### 5. 高频易错点

- Program 不是 portfolio。
- PMO 不是某一个具体项目。
- 项目组合更偏战略选择和资源统筹。

## 9. 组织结构与零散管理科学考点

### 1. 常见组织结构

- 职能型：项目经理权力较弱
- 矩阵型：需要协商资源
- 项目型：项目经理权力较强，资源更集中

### 2. 高频判断点

- 职能型组织里，项目经理通常更依赖协调。
- 项目型组织里，项目经理对资源和决策的控制力通常更强。
- 矩阵型组织最常考的是资源协商和双重汇报关系。

## 10. 今天最容易混的概念

| 易混概念 | 正确区分 |
| --- | --- |
| issue vs risk | 一个已经发生，一个尚未发生 |
| deliverable vs milestone | 一个是交付物，一个是关键节点 |
| baseline vs benchmark | 一个是受控依据，一个是对照参考 |
| OPA vs EEF | 一个是组织资产，一个是环境因素 |
| law vs guideline | 一个强制性更高，一个更多是指导 |
| PMO vs CCB | 一个是组织级治理支持，一个是变更评审决策机制 |

## 八、案例题

### 案例 1：英文邮件阅读与项目响应

请阅读下面邮件：

Subject: Delivery Delay and Revised Test Plan

Due to a firmware compatibility issue identified during integration testing, the vendor needs three additional working days to provide a patched build. Please do not deploy the current version to production. We will submit the revised schedule and updated test report by EOD Thursday.

问题：

1. 这封邮件里已经明确暴露出的是什么问题。
2. 邮件中 “do not deploy the current version to production” 反映了哪类管理关注点。
3. 作为项目经理，你接下来最应同步更新哪些内容或动作。

参考答题方向：

- 已暴露的问题：集成测试中发现固件兼容性问题，供应商交付延迟。
- 管理关注点：版本受控、上线风险控制、禁止带缺陷版本直接进入生产环境。
- 后续动作：更新问题日志和进度安排，确认 revised schedule，跟踪 updated test report，评估对里程碑和风险的影响，并按需要升级沟通。

### 案例 2：职业道德与零散高频点综合判断

某项目进入关键验收阶段时，出现了以下情况：

1. 供应商希望项目经理“通融一下”，先通过验收，后补齐文档。
2. 团队成员为赶时间，建议复用一个未购买授权的第三方组件。
3. 业务部门要求直接导出一批包含敏感信息的数据发到公共群里，理由是“方便大家核对”。
4. 项目组已有多个类似项目，但新人完全没有查阅组织模板和历史经验，而是从头各自编写材料。

问题：

1. 上述场景至少涉及哪 4 类高频考点。
2. 作为项目经理，你分别应采取什么处理动作。
3. 如果把这类内容放到 day13 的速记表里，你会如何分类整理。

参考答题方向：

- 涉及考点：职业道德、知识产权、保密义务、OPA 复用、验收与合规边界。
- 处理动作：不满足条件不得验收；禁止使用未授权组件；敏感数据只向授权对象按最小必要原则披露；优先复用组织模板和经验教训。
- 分类整理方式：诚信与公平、知识产权、保密义务、组织级资产四栏分类。
