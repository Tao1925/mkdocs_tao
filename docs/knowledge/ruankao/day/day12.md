# 第 12 天：信息安全、工程监理、配置管理与变更管理

## 一、今天的目标

第 12 天进入信息系统项目管理师里另一个典型“覆盖面广、概念边界多、案例答题非常容易失分”的综合模块：信息安全、工程监理、配置管理与变更管理。

这一模块的特点是：

- 综合知识会考安全目标、安全措施、备份恢复、访问控制、审计、监理职责、四控三管一协调、配置项、基线、版本控制、变更控制流程等高频概念。
- 案例分析经常把“需求变化、配置混乱、版本失控、上线回退失败、监理缺位、安全措施不足”混在一个场景里，要求你从项目管理角度拆解问题。
- 论文题可能直接命题为配置管理、变更管理，也可能在整体管理、质量管理、风险管理、安全管理等主题中间接考查这些能力。
- 很多考生会把“配置管理”“变更管理”“版本管理”“发布管理”“监理监督”“安全控制”混为一谈，导致综合题和案例题同时丢分。

- 配置管理

## 四、今天要掌握的核心知识

## 1. 信息安全的基本目标

今天必须记住的三个核心词是：

1. 保密性
2. 完整性
3. 可用性

### 1. 保密性

强调：

- 信息只被被授权的人访问
- 防止未授权泄露

### 2. 完整性

强调：

- 信息和系统内容不被未授权篡改
- 保持准确、完整、一致

### 3. 可用性

强调：

- 在需要时系统和数据可被正常访问和使用

### 4. 高频易错点

- 保密性不是“谁都看不到”，而是未经授权的人看不到。
- 可用性不是“永不故障”，而是出现故障时也要尽量保障业务连续性。

## 2. 常见安全控制措施

### 1. 身份鉴别与访问控制

更强调：

- 谁能进系统
- 进来后能看什么、做什么

### 2. 备份与恢复

更强调：

- 数据丢失后能不能恢复
- 系统故障后业务能不能恢复

### 3. 日志审计与监控

更强调：

- 关键操作是否可追溯
- 异常行为是否能被发现

### 4. 边界防护与恶意代码防范

更强调：

- 防止非法访问
- 防止恶意软件、木马、病毒等破坏

### 5. 高频判断法

- 防泄露看保密性
- 防篡改看完整性
- 防中断看可用性

## 3. 工程监理的典型职责

### 1. 为什么监理会考

因为软考会从“第三方监督与控制”角度考你是否理解：

- 项目不是只靠承建方自己说了算
- 重大项目往往需要独立监督、过程控制和质量把关

### 2. 常见理解框架

常用记忆法是：

- 四控
- 三管
- 一协调

### 3. 可以先这样理解

- 四控：控制质量、进度、投资、变更
- 三管：合同管理、信息管理、安全管理
- 一协调：协调有关单位和关系

### 4. 高频边界

- 监理是监督、审核、协调，不是替代建设单位或承建单位做项目执行。
- 监理不能代替项目经理拍板所有业务决策。

## 4. 配置管理主线

今天必须记住的配置管理链条是：

1. 配置管理规划
2. 识别配置项
3. 建立基线
4. 版本控制与状态记录
5. 配置审计

### 1. 配置项是什么

配置项就是需要纳入受控管理的对象，例如：

- 需求文档
- 设计文档
- 源代码
- 测试用例
- 部署脚本
- 运行环境配置

### 2. 基线是什么

基线强调：

- 经正式评审确认后作为后续工作的依据版本
- 一旦建立，不可随意改动

### 3. 状态记录做什么

状态记录强调：

- 当前版本是什么
- 谁改过
- 改了什么
- 何时发布

### 4. 配置审计做什么

配置审计强调：

- 实际配置是否和记录一致
- 是否按规定流程实施变更

## 5. 变更管理主线

今天必须记住的变更管理链条是：

1. 提出变更
2. 记录变更
3. 影响分析
4. 评审审批
5. 实施变更
6. 验证结果
7. 更新文档和基线

### 1. 变更不是坏事

项目中有变化很正常。

真正的问题不是发生变化，而是：

- 变化没有登记
- 没有评估影响
- 没有审批
- 没有同步更新文档、计划和配置状态

### 2. 变更为什么容易失控

因为很多项目里的变化往往来自：

- 用户新增需求
- 技术方案调整
- 缺陷修复引发二次改动
- 供应商交付变化
- 安全要求升级

### 3. 高频易错点

- 变更不能只改代码不改文档。
- 变更不能只让开发知道、不让测试和运维知道。
- 变更审批通过后，还要更新计划、基线和配置状态。

## 6. 配置管理与变更管理的关系

### 1. 为什么这两个模块总被放在一起考

因为它们是一前一后的关系：

- 配置管理解决“哪些东西要管、当前版本是什么”。
- 变更管理解决“这些东西要改时怎么改、谁批准、怎么留痕”。

### 2. 快速理解法

- 没有配置管理，变更不知道改的是哪个版本。
- 没有变更管理，配置状态就会越来越乱。

### 3. 高频考法

- 多人并行开发导致版本混乱
- 生产环境修改未留痕
- 缺陷修复后未更新配置库
- 变更通过后计划和文档未同步

## 7. 发布、回退与环境一致性

### 1. 为什么这是案例高频点

因为很多项目不是不会开发，而是：

- 上线包拿错了
- 测试环境和生产环境不一致
- 回退方案没准备
- 紧急修复没纳入配置控制

### 2. 应掌握的基本思路

- 发布前确认版本、依赖、脚本、数据和环境一致性
- 发布时留痕、审批、验证
- 发布后若失败，按预案回退

### 3. 高频陷阱

- 紧急上线不是跳过流程的理由
- 补丁修复也属于变更，也要受控

## 8. 安全、监理、配置、变更如何在案例里串起来

### 1. 典型问题链条

一个常见失败链条是：

- 权限控制不足
- 变更未审批
- 配置项未更新
- 监理未发现或未推动整改
- 上线后出现安全或稳定性问题

### 2. 标准答题链条

碰到这类综合场景时，可以按下面顺序组织答案：

1. 指出安全控制缺失
2. 指出配置和版本管理缺失
3. 指出变更未走流程
4. 指出监理监督与留痕不足
5. 给出整改动作和长期机制

## 9. 论文怎么写得不空

### 1. 常见空话风险

很多人写配置和变更管理，只会写：

- 我建立了变更流程
- 我加强了版本管理
- 我严格审批所有变更

这些话都对，但没有项目味。

### 2. 更好的写法

应写出：

- 管理的配置项有哪些
- 哪些阶段建立了哪些基线
- 变更来源有哪些
- CCB 如何组织
- 如何评估对范围、进度、成本、质量、安全的影响
- 如何同步更新代码、文档、测试和部署环境

### 3. 推荐表达链条

配置识别 -> 建立基线 -> 提出变更 -> 影响分析 -> CCB 审批 -> 实施验证 -> 更新状态 -> 审计复盘

## 10. 今天最容易混的概念

| 易混概念 | 正确区分 |
| --- | --- |
| 保密性 vs 完整性 | 一个防泄露，一个防篡改 |
| 配置项 vs 基线 | 一个是对象，一个是被确认的受控版本 |
| 版本控制 vs 变更控制 | 一个管版本流转，一个管变更审批和实施 |
| 配置审计 vs 验收测试 | 一个查配置与流程一致性，一个查功能或性能是否达标 |
| 监理监督 vs 项目执行 | 一个监督协调，一个直接实施 |
| 紧急修复 vs 可跳过流程 | 紧急不等于无流程，仍需受控和留痕 |

## 八、案例题

### 案例 1：紧急上线引发的版本与安全问题

某市智慧园区综合管理平台在试运行前一周发现移动端审批模块存在严重缺陷。开发负责人安排工程师在生产环境直接修改配置文件和脚本，并在当天晚上重新部署。由于时间紧张，未提交正式变更申请，也未同步更新配置库、测试记录和部署清单。上线后系统虽然恢复可用，但第二天发现部分离岗人员仍可访问敏感审批数据，且审计日志缺失，无法准确还原谁做过哪些操作。

问题：

1. 该场景至少暴露出哪 5 个管理问题。
2. 项目经理应如何组织紧急整改。
3. 从配置与变更管理角度，后续应建立哪些长期机制。

参考答题方向：

- 识别问题：未受控变更、生产环境直接修改、配置库未更新、权限控制不足、日志审计缺失、环境与记录不一致。
- 整改动作：补做变更登记、核查生产版本、补充审计日志、立即清理高权限账号、重新核对配置项和基线、组织回归验证。
- 长期机制：紧急变更流程、发布审批、环境一致性检查、权限矩阵定期复核、配置审计与留痕制度。

### 案例 2：监理发现配置失控与频繁需求变更

某园区综合平台项目进入联调期后，建设单位频繁提出优化需求。承建单位为了赶进度，常常先口头答应并直接调整代码和接口文档，之后再补手续。监理在周检查中发现：需求文档、设计文档、测试用例和实际系统版本经常对不上；部分变更没有 CCB 记录；测试环境和生产预发布环境参数不一致；项目组也没有形成统一的配置项清单和基线发布记录。

问题：

1. 监理在该场景下应重点指出哪些问题。
2. 项目经理应如何从配置管理和变更管理两个维度纠偏。
3. 如果把这一段写进论文，怎样体现“管理动作”而不只是“发现了问题”。

参考答题方向：

- 重点问题：变更未受控、配置项识别不完整、基线不清、环境不一致、监理发现问题后的整改闭环不足。
- 纠偏动作：建立配置项清单、确定阶段基线、所有变更统一登记分析审批、更新文档和测试资产、对环境参数统一校验。
- 论文表达：写清楚建立 CCB、发布清单、配置审计、环境核对和监理整改闭环等具体动作。
