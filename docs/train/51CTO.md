<h2 id="Shell">Shell</h2>

### 基础介绍

Shell 是 Linux/Unix 系统中的命令解释器，也是桌面运维最常见的自动化入口。
它的价值不只是“会敲命令”，而是能够把零散操作变成稳定、可复用、可批量执行的流程。
桌面运维场景里，Shell 常用于巡检系统状态、处理日志、修改配置、分发脚本、维护账号权限、调用系统命令和编排简单任务流。
如果说命令行是“单次动作”，Shell 脚本就是“把动作标准化”的第一层能力。

### 关键知识

#### 1. Shell、Bash、sh 的关系

| 概念 | 说明 | 运维中的意义 |
| --- | --- | --- |
| Shell | 命令解释器的总称 | 负责读取命令、解释语法、调用系统程序 |
| sh | 传统 Bourne Shell 接口或兼容层 | 常用于追求兼容性的脚本头 |
| bash | GNU Bash，是最常见的 Shell 实现 | 语法丰富，支持数组、函数、算术、补全等 |
| zsh | 交互能力强，补全体验好 | 适合个人终端，但生产脚本一般仍优先 Bash |

- 终端是用户交互界面，Shell 是终端中真正负责解释命令的程序。
- 开发机和生产机默认 Shell 可能不一样，所以脚本头必须写清楚。
- 交互习惯可以是 zsh，但脚本交付最好明确为 bash 或 sh，避免在其他机器上出现兼容性问题。
- 考试里常见误区是把 Shell 和终端、bash 和 sh 当成完全相同的概念。

#### 2. 脚本执行方式与运行环境

| 执行方式 | 写法 | 特点 | 典型场景 |
| --- | --- | --- | --- |
| 指定解释器执行 | `bash script.sh` | 不需要脚本可执行权限 | 临时执行、调试 |
| 可执行文件方式 | `chmod +x script.sh` 后 `./script.sh` | 依赖脚本头解释器 | 正式脚本、计划任务 |
| source 方式 | `source script.sh` 或 `. script.sh` | 在当前 Shell 中执行 | 加载环境变量、别名、函数 |

- `bash script.sh` 会启动一个新的 Bash 进程。
- `source script.sh` 不会新开子进程，而是在当前会话中直接执行。
- 因为 `source` 改的是当前会话，所以常用于激活虚拟环境、加载变量和初始化函数。
- 如果脚本里有 `export PATH=...`，想让修改留在当前终端，就要用 `source`。

```bash
#!/bin/bash

echo "PID=$$"
echo "SHELL=$SHELL"
echo "USER=$USER"
```

- `#!/bin/bash` 表示用 Bash 解释执行。
- `$$` 表示当前脚本进程 PID。
- 题目很爱考 `source` 与直接执行的区别，本质是“是否在当前会话生效”。

#### 3. 变量、环境变量与位置参数

| 类型 | 示例 | 说明 | 易错点 |
| --- | --- | --- | --- |
| 普通变量 | `name="alice"` | 当前 Shell 或脚本内部使用 | 等号两边不能加空格 |
| 环境变量 | `export JAVA_HOME=/opt/jdk` | 子进程可继承 | 只写变量不 export，外部程序可能看不到 |
| 只读变量 | `readonly VERSION=1.0` | 禁止后续修改 | 常用于固定配置 |
| 局部变量 | `local file=/tmp/a.log` | 仅函数内部可见 | 只能在函数内部用 |

| 特殊参数 | 含义 | 常见用途 |
| --- | --- | --- |
| `$0` | 脚本名 | 打印帮助信息 |
| `$1` `$2` | 第 1、2 个参数 | 传入文件名、主机名、用户 |
| `$#` | 参数个数 | 判断入参数量 |
| `$@` | 所有参数，保留边界 | 适合循环透传参数 |
| `$*` | 所有参数，易被拼成一个字符串 | 不如 `$@` 安全 |
| `$?` | 上一条命令退出码 | 判断命令成功失败 |
| `$$` | 当前进程 PID | 临时文件命名 |
| `$!` | 后台任务 PID | 监控后台进程 |

- Shell 变量本质上都是字符串，算术时要用 `$(( ))`。
- `export` 的作用不是“声明变量”，而是“让子进程能看到这个变量”。
- `"$@"` 与 `"$*"` 的差别是高频陷阱。
- 绝大多数场景下，写循环透传参数都优先用 `"$@"`。

```bash
#!/bin/bash

echo "script=$0"
echo "count=$#"
for arg in "$@"; do
    echo "arg=$arg"
done
```

#### 4. 引号、转义与展开机制

| 写法 | 含义 | 示例 |
| --- | --- | --- |
| 单引号 `' '` | 强引用，不做变量和命令替换 | `'${HOME}'` 原样输出 |
| 双引号 `" "` | 弱引用，会做变量和命令替换 | `"$HOME"` |
| 反斜杠 `\` | 转义单个特殊字符 | `\$`、`\n` |
| 命令替换 | 执行命令并取输出 | `$(date)` |
| 算术扩展 | 进行整数运算 | `$((1+2))` |
| 花括号扩展 | 快速生成序列或字符串模板 | `{1..5}`、`file_{a,b}` |
| 通配展开 | 根据文件名匹配 | `*.log` |

- 单引号最安全，适合写固定字符串。
- 双引号最常用，适合变量拼接和路径处理。
- 没加引号时，变量中的空格会被 Shell 再次分词，导致脚本出现隐蔽错误。
- 运维脚本中处理路径、用户名、文件名时，几乎都应该给变量加双引号。

```bash
file_name="/tmp/my log.txt"
echo "$file_name"
ls "$file_name"
```

- 上例中如果写成 `ls $file_name`，会被拆成两个参数。
- 题目常用“路径带空格”“参数为空字符串”来考你是否养成加引号的习惯。

#### 5. 条件判断与测试表达式

| 测试项 | 含义 |
| --- | --- |
| `-f file` | 是否为普通文件 |
| `-d dir` | 是否为目录 |
| `-e path` | 路径是否存在 |
| `-r file` | 是否可读 |
| `-w file` | 是否可写 |
| `-x file` | 是否可执行 |
| `-n str` | 字符串非空 |
| `-z str` | 字符串为空 |
| `a = b` | 字符串相等 |
| `a != b` | 字符串不等 |
| `-eq -ne -gt -lt -ge -le` | 整数比较 |

| 写法 | 特点 | 备注 |
| --- | --- | --- |
| `[ ... ]` | 传统测试写法 | 两边必须留空格 |
| `[[ ... ]]` | Bash 增强写法 | 更安全，支持模式匹配 |
| `(( ... ))` | 算术判断 | 适合整数运算 |

- 考试里常考 `[ ]` 两边空格问题。
- `[[ ]]` 在处理字符串和模式匹配时更稳。
- 运维脚本里判断文件存在、服务状态、参数是否合法，基本都离不开条件判断。

```bash
if [[ -z "$1" ]]; then
    echo "usage: $0 <service_name>"
    exit 1
fi
```

#### 6. 流程控制与函数

| 结构 | 适用场景 | 说明 |
| --- | --- | --- |
| `if / elif / else` | 多条件分支 | 最常见 |
| `case` | 固定选项分支 | 比多层 if 更清楚 |
| `for` | 遍历列表、文件、主机 | 批量运维常见 |
| `while` | 条件为真就循环 | 轮询、读取文件 |
| `until` | 条件为假时循环 | 与 while 逻辑相反 |
| `function` | 复用逻辑 | 脚本模块化 |

- `for` 更适合处理清单。
- `while read line` 更适合逐行读取文件。
- `case` 特别适合处理 `start/stop/restart/status` 这种运维参数。
- 函数能让大脚本拆分成多个可维护的小模块。

```bash
#!/bin/bash

operate_service() {
    local action="$1"
    case "$action" in
        start) systemctl start nginx ;;
        stop) systemctl stop nginx ;;
        restart) systemctl restart nginx ;;
        status) systemctl status nginx ;;
        *) echo "unsupported action"; return 1 ;;
    esac
}

operate_service "$1"
```

#### 7. 重定向、管道与命令组合

| 写法 | 含义 | 典型用法 |
| --- | --- | --- |
| `>` | 覆盖写入标准输出 | 写日志文件 |
| `>>` | 追加写入标准输出 | 持续追加日志 |
| `2>` | 重定向标准错误 | 单独记录错误 |
| `2>&1` | 错误流并入标准输出 | 收集完整输出 |
| `|` | 前一命令输出作为后一命令输入 | 组合多条命令 |
| `tee` | 一边显示一边写文件 | 调试和留痕 |

- 退出码比输出文字更重要。
- 很多脚本表面看“有输出”，但实际上命令已经失败，所以要结合 `$?` 判断。
- 生产脚本里记录日志时，经常需要把 stdout 和 stderr 一起落盘。

```bash
df -h | grep -v tmpfs | tee /tmp/disk_check.log
systemctl status nginx > /tmp/nginx_status.log 2>&1
```

#### 8. 文本处理三件套与批量运维命令

| 命令 | 作用 | 高频场景 |
| --- | --- | --- |
| `grep` | 过滤匹配行 | 日志检索、配置检查 |
| `sed` | 行级替换和编辑 | 批量改配置 |
| `awk` | 按列和规则处理文本 | 统计、格式化、抽取字段 |
| `cut` | 切列 | 提取某一列 |
| `sort` | 排序 | 排序用户或日志 |
| `uniq` | 去重 | 去重 IP、用户名 |
| `tr` | 字符替换 | 转大小写、删字符 |
| `xargs` | 把输入转成参数 | 批量删除、批量执行 |
| `find` | 查找文件 | 配合执行操作 |

- `grep` 偏“找”。
- `sed` 偏“改”。
- `awk` 偏“算”和“抽”。
- 真正的运维效率，往往不是会多少命令，而是会不会把命令串起来解决问题。

```bash
# 查找包含 error 的日志行
grep -i "error" /var/log/messages

# 替换配置文件中的旧 IP
sed -i 's/10.0.0.1/10.0.0.2/g' app.conf

# 统计监听端口数量
ss -tuln | awk 'NR>1 {print $5}' | awk -F: '{print $NF}' | sort | uniq -c
```

#### 9. 健壮性、调试与安全意识

| 技术点 | 作用 | 说明 |
| --- | --- | --- |
| `set -e` | 命令失败时退出 | 减少错上加错 |
| `set -u` | 使用未定义变量时报错 | 防止变量拼写错误 |
| `set -o pipefail` | 管道任一命令失败即失败 | 避免掩盖错误 |
| `bash -x script.sh` | 打印执行轨迹 | 调试脚本常用 |
| `trap` | 捕获信号或退出动作 | 做清理和回滚 |
| `shellcheck` | 静态检查脚本 | 提前发现语法与风格问题 |

- 强烈建议把生产脚本写成“先校验、再执行、最后记录结果”的模式。
- 绝不要在脚本里硬编码密码、私钥和敏感令牌。
- 需要执行危险命令时，先打印目标对象，再加确认逻辑。
- 删除文件、改配置、停服务这类操作都应该加日志和退出码判断。

```bash
#!/bin/bash
set -euo pipefail

tmp_file="/tmp/check_$$.txt"
trap 'rm -f "$tmp_file"' EXIT

echo "start $(date)" > "$tmp_file"
systemctl is-active sshd >> "$tmp_file"
cat "$tmp_file"
```

#### 10. 计划任务与服务化思维

| 工具 | 场景 | 说明 |
| --- | --- | --- |
| `crontab` | 固定时间执行 | 如凌晨备份、定时巡检 |
| `at` | 一次性延迟任务 | 临时计划操作 |
| `systemd timer` | 更现代的定时方式 | 和 systemd 服务体系统一 |

- `cron` 很适合做定时巡检、日志清理、缓存清理、备份任务。
- 需要高可观测性时，`systemd timer` 往往比 `cron` 更容易查日志和管状态。
- 考试常考 `cron` 表达式含义，例如“每天凌晨 2 点执行”“每 5 分钟执行一次”。

```bash
# 每天凌晨 2 点执行巡检脚本
0 2 * * * /opt/scripts/check_system.sh

# 每 5 分钟执行一次
*/5 * * * * /opt/scripts/check_port.sh
```

#### 11. Shell 与 Python 的边界

| 场景 | 更适合 Shell | 更适合 Python |
| --- | --- | --- |
| 调系统命令 | 很合适 | 也可以，但更重 |
| 批量改配置 | 很合适 | 适合复杂逻辑 |
| 文本轻处理 | 很合适 | 适合复杂规则 |
| JSON 和 API | 不太方便 | 更适合 |
| 复杂报表 | 一般 | 明显更适合 |
| 长期维护脚本 | 小脚本可行 | 中大型脚本更优 |

- Shell 是轻量编排器。
- Python 是更完整的自动化语言。
- 桌面运维实际工作中，两者经常组合使用，而不是非此即彼。

#### 12. 常见运维脚本思路

| 场景 | 核心动作 | 注意事项 |
| --- | --- | --- |
| 主机巡检 | CPU、内存、磁盘、端口、服务状态 | 输出要结构化 |
| 日志清理 | 查目录、判断时间、删除过期文件 | 谨慎处理路径 |
| 服务保活 | 判断服务状态、异常重启、告警 | 防止重启风暴 |
| 账户维护 | 创建用户、改权限、过期清理 | 记录操作审计 |
| 配置分发 | 备份旧文件、替换新文件、重载服务 | 一定要先校验 |

```bash
#!/bin/bash
set -euo pipefail

service_name="nginx"
log_file="/tmp/service_check.log"

if systemctl is-active --quiet "$service_name"; then
    echo "$(date '+%F %T') $service_name ok" >> "$log_file"
else
    echo "$(date '+%F %T') $service_name failed, restart" >> "$log_file"
    systemctl restart "$service_name"
fi
```

### 高频考点

#### 常见概念题

- `source script.sh` 与 `./script.sh` 的区别是是否在当前 Shell 生效。
- `#!/bin/bash` 与 `#!/bin/sh` 的区别本质上是解释器与兼容性边界不同。
- 普通变量和环境变量的区别在于子进程是否可见。
- `$?` 是上一条命令退出码，`0` 通常表示成功。
- `"$@"` 和 `"$*"` 的区别是参数边界是否保留。

#### 常见比较题

- 单引号不展开变量，双引号会展开变量和命令替换。
- `[` 更传统，`[[` 更安全、更适合 Bash。
- `for` 适合遍历清单，`while read` 适合逐行处理文件。
- `grep` 偏检索，`sed` 偏替换，`awk` 偏按字段和规则处理。
- `cron` 适合简单定时，`systemd timer` 更适合需要统一日志和状态管理的环境。

#### 常见场景题

- 路径中有空格时没有加双引号，会导致脚本异常。
- 批量删除文件前不做 `echo` 预演，属于高风险写法。
- 修改配置后不做语法校验就重载服务，是典型的运维失误。
- 管道末尾命令成功不代表整条管道成功，所以要考虑 `pipefail`。
- 在脚本中直接写明文密码，属于安全隐患。

#### 容易出现在题目里的细节

- 判断目录要用 `-d`，判断普通文件要用 `-f`。
- `case` 特别适合处理服务动作分支。
- 计划任务默认环境变量少，脚本里最好写全路径。
- `chmod 755`、`644` 之类的数字权限经常与 `rwx` 对应关系一起考。
- `trap` 可用于脚本退出时清理临时文件。


<h2 id="Python">Python</h2>

### 基础介绍

Python 是桌面运维和自动化场景中最常见的脚本语言之一。
它比 Shell 更擅长做复杂逻辑、结构化数据处理、接口调用和报表生成。
对于桌面运维工程师来说，Python 的价值不在于刷算法题，而在于把重复操作、巡检任务和系统数据加工做得更稳定、更可维护。
只会零散命令的人是“能干活”，会写 Python 的人更容易把经验沉淀成工具。

### 关键知识

#### 1. Python 在桌面运维中的定位

| 方向 | 说明 | 典型任务 |
| --- | --- | --- |
| 自动化脚本 | 调命令、批量处理、生成结果 | 巡检、批量配置、日志解析 |
| 接口调用 | 访问 HTTP API、资产系统、工单系统 | 拉资产清单、推送告警 |
| 数据处理 | 结构化处理文本、JSON、CSV、Excel | 出周报、导表、做汇总 |
| 小工具开发 | 写轻量命令行工具或内部脚本平台 | 资产查询、账号查询 |

- Python 不一定替代 Shell，而是补足 Shell 在结构化处理和复杂逻辑上的弱点。
- 内部考试通常更关注“工具思维”和“自动化思路”，而不是语言细枝末节。
- 如果你已经有大量 Linux 基础，学习 Python 的路径会比纯开发方向更快。

#### 2. 基础语法与核心数据结构

| 数据结构 | 特点 | 适用场景 |
| --- | --- | --- |
| `list` | 有序、可变 | 存放主机列表、文件列表 |
| `tuple` | 有序、不可变 | 固定配置项、键值对 |
| `dict` | 键值映射 | 资产信息、接口返回数据 |
| `set` | 无序、去重 | 去重用户、去重主机、去重端口 |
| `str` | 文本字符串 | 日志行、命令输出 |

- 运维脚本里最常见的三种结构是 `list`、`dict` 和 `str`。
- `dict` 是接口和 JSON 处理的核心。
- `set` 在去重和交集、差集场景里非常好用。
- 题目里喜欢考“列表可变、元组不可变”“字典通过键访问”“集合天然去重”。

```python
servers = ["pc-001", "pc-002", "pc-003"]
status = {"pc-001": "ok", "pc-002": "down"}
unique_users = set(["alice", "bob", "alice"])

print(servers[0])
print(status["pc-001"])
print(unique_users)
```

#### 3. 文件处理是运维脚本基本功

| 文件类型 | 常见库 | 用途 |
| --- | --- | --- |
| 纯文本 | `open` | 读日志、写结果 |
| JSON | `json` | 接口报文、配置文件 |
| CSV | `csv` | 导出表格、资产清单 |
| Excel | `openpyxl` | 生成给管理层的报表 |
| YAML | `yaml` | 配置管理、自动化工具配置 |

- 读文件最好用 `with open(...) as f:`，这样会自动关闭文件句柄。
- 编码问题是中文环境里最常见的坑，写文件时最好明确 `encoding="utf-8"`。
- 结构化存储优先 JSON 或 CSV，少依赖“手工拼字符串”。

```python
from pathlib import Path

log_path = Path("/tmp/check.log")
log_path.write_text("service ok\n", encoding="utf-8")
content = log_path.read_text(encoding="utf-8")
print(content)
```

#### 4. 标准库里最常用的几个模块

| 模块 | 作用 | 桌面运维场景 |
| --- | --- | --- |
| `os` | 环境变量、系统信息、路径操作 | 读取环境、目录处理 |
| `pathlib` | 面向对象的路径处理 | 替代手工拼接路径 |
| `subprocess` | 调用系统命令 | 执行 `ipconfig`、`systemctl`、`tasklist` |
| `json` | JSON 编解码 | API 数据交换 |
| `logging` | 日志记录 | 脚本运行留痕 |
| `argparse` | 解析命令行参数 | 命令行工具 |
| `datetime` | 时间处理 | 统计、切日志、报表 |
| `shutil` | 文件和目录操作 | 拷贝、移动、打包 |

- `pathlib` 比 `os.path` 可读性更好。
- `subprocess.run()` 是运维脚本里非常高频的能力。
- `logging` 不是锦上添花，而是脚本长期维护的基础设施。

```python
import subprocess

result = subprocess.run(
    ["systemctl", "status", "sshd"],
    capture_output=True,
    text=True,
)

print(result.returncode)
print(result.stdout)
print(result.stderr)
```

#### 5. 调系统命令时的注意事项

| 关注点 | 说明 | 风险 |
| --- | --- | --- |
| 返回码 | 通过 `returncode` 判断成功失败 | 只看 stdout 容易误判 |
| 标准输出与错误输出 | `stdout` 与 `stderr` 分开读取 | 错误信息可能不在 stdout |
| 超时 | `timeout=` 防止命令卡死 | 巡检批处理很重要 |
| 参数传递 | 用列表形式传参更安全 | 避免注入和转义问题 |
| `shell=True` | 仅在必要时使用 | 存在命令注入风险 |

- 一般优先写成 `subprocess.run(["cmd", "arg1", "arg2"])`。
- 除非确实要执行复杂管道或重定向，否则不推荐 `shell=True`。
- 批量巡检时，要考虑某台机器命令卡住导致整体任务挂死。

#### 6. API 与网络请求处理

| 能力 | 工具 | 说明 |
| --- | --- | --- |
| GET 请求 | `requests.get` | 拉资产、查工单、查状态 |
| POST 请求 | `requests.post` | 提交工单、发告警、改状态 |
| Session | `requests.Session()` | 保持会话、复用连接 |
| 超时与重试 | `timeout`、配合重试逻辑 | 防止脚本长时间阻塞 |
| JSON 解析 | `response.json()` | 处理结构化结果 |

- 请求一定要设置超时。
- 不能假设接口永远成功，必须考虑 4xx、5xx、超时和返回字段缺失。
- 运维脚本里常见的失败不是代码报错，而是接口返回结构不符合预期。

```python
import requests

response = requests.get("https://example.com/api/status", timeout=5)
response.raise_for_status()
data = response.json()
print(data)
```

#### 7. 日志、配置和参数化

| 模块 | 作用 | 运维价值 |
| --- | --- | --- |
| `logging` | 记录运行日志 | 便于排障和追踪 |
| `argparse` | 接收命令行参数 | 脚本复用性更高 |
| `configparser` | 读取 INI 配置 | 分离代码与参数 |
| 环境变量 | 存放敏感或环境差异配置 | 避免写死路径和密钥 |

- 真正能长期用的脚本，一般都不是“把所有参数写死在代码里”。
- 命令行参数适合临时输入。
- 配置文件适合固定参数。
- 环境变量适合路径、秘钥、环境切换等内容。

```python
import argparse
import logging

parser = argparse.ArgumentParser()
parser.add_argument("--host", required=True)
args = parser.parse_args()

logging.basicConfig(level=logging.INFO)
logging.info("checking host=%s", args.host)
```

#### 8. 异常处理与健壮性

| 语法 | 用途 |
| --- | --- |
| `try` | 包裹可能出错的逻辑 |
| `except` | 捕获并处理异常 |
| `finally` | 无论是否出错都执行 |
| `raise` | 主动抛出异常 |

- 运维脚本不怕报错，怕的是默默失败。
- 应优先让脚本在错误时给出清楚的上下文，例如“哪台主机失败、哪个接口失败、参数是什么”。
- 不推荐大量裸 `except:`，这会把真正的问题吞掉。

```python
try:
    result = int("123")
except ValueError as exc:
    print(f"convert failed: {exc}")
finally:
    print("done")
```

#### 9. 虚拟环境与依赖管理

| 命令 | 作用 |
| --- | --- |
| `python -m venv .venv` | 创建虚拟环境 |
| `source .venv/bin/activate` | 激活虚拟环境 |
| `pip install requests` | 安装依赖 |
| `pip freeze > requirements.txt` | 导出依赖 |
| `pip install -r requirements.txt` | 按文件安装依赖 |

- 虚拟环境的意义是“让不同脚本、不同项目的依赖不要互相污染”。
- 在企业环境中，脚本能不能稳定复现，依赖管理是关键。
- 考试里常考 `venv`、`pip`、`requirements.txt` 的基本用途。

#### 10. 并发与性能意识

| 方式 | 适用场景 | 说明 |
| --- | --- | --- |
| 多线程 | I/O 密集型，如多主机巡检 | 网络等待多时效果明显 |
| 多进程 | CPU 密集型 | 运维场景相对少 |
| 异步 | 大量网络请求 | 要求更高，不是初学优先项 |

- 大多数桌面运维脚本瓶颈在网络和磁盘，不在 CPU。
- 所以理解“批量巡检属于 I/O 密集场景”比死背并发概念更重要。
- 内部考试一般不会深挖 GIL，但可能问“为什么批量请求比串行快”。

#### 11. 一个更接近运维工作的脚本结构

```python
from pathlib import Path
import json
import logging
import subprocess

logging.basicConfig(level=logging.INFO)


def check_service(name: str) -> dict:
    result = subprocess.run(
        ["systemctl", "is-active", name],
        capture_output=True,
        text=True,
    )
    return {
        "service": name,
        "status": result.stdout.strip(),
        "returncode": result.returncode,
    }


def main() -> None:
    data = check_service("sshd")
    Path("result.json").write_text(
        json.dumps(data, ensure_ascii=False, indent=2),
        encoding="utf-8",
    )
    logging.info("check finished: %s", data)


if __name__ == "__main__":
    main()
```

- 这类脚本体现的是结构化输出、函数拆分和日志留痕。
- 真正可交付的内部工具，一般都具备这三个特征。

#### 12. Python 与 Shell 的互补关系

| 任务 | Shell 优势 | Python 优势 |
| --- | --- | --- |
| 单机命令编排 | 很强 | 一般 |
| 复杂字符串和 JSON | 一般 | 很强 |
| API 请求 | 弱 | 很强 |
| 结构化报表 | 弱 | 很强 |
| 快速改配置 | 很强 | 中等 |
| 中大型脚本维护 | 一般 | 更强 |

- 轻量命令编排用 Shell。
- 复杂逻辑与结构化处理用 Python。
- 真正成熟的运维工具链往往是 Bash 调用 Python，或 Python 里调用系统命令。

### 高频考点

#### 常见概念题

- `list` 有序可变，`tuple` 有序不可变，`set` 去重，`dict` 键值映射。
- `with open(...)` 的优势是自动关闭文件。
- `subprocess.run()` 返回码比字符串输出更可靠。
- `logging` 的价值在于留痕，而不是简单 `print`。
- `venv` 的作用是隔离依赖环境。

#### 常见比较题

- Shell 更擅长命令编排，Python 更擅长结构化处理和接口调用。
- `os.path` 与 `pathlib` 都能处理路径，但 `pathlib` 可读性更好。
- `print` 适合临时输出，`logging` 适合长期维护。
- `requests.get()` 一定要配合超时和异常处理。
- `shell=True` 灵活但风险高。

#### 常见场景题

- 批量巡检时不设置超时，可能导致整个任务卡死。
- 从接口返回 JSON 时，不判断状态码就直接取字段，容易报错。
- 直接把用户名、密码写进脚本源码，属于安全风险。
- 用 Excel 做长期数据源不如用 CSV/JSON 稳定。
- 脚本只输出中文说明、不输出结构化结果，不利于二次处理。

#### 容易出现在题目里的细节

- `requirements.txt` 是依赖复现的重要文件。
- `response.raise_for_status()` 能把 HTTP 错误快速显式抛出。
- `argparse` 能让脚本做成可复用命令行工具。
- `try/except/finally` 往往与文件、网络、子进程场景一起考。
- 桌面运维考试里的 Python，重点不是面向对象，而是自动化落地能力。


<h2 id="流程、运维、监控、配置平台">流程、运维、监控、配置平台</h2>

### 基础介绍

桌面运维并不只是装系统、修故障和处理账号问题。
真正成熟的运维体系一定要有流程、监控、配置和平台化支撑。
流程解决“怎么做才不乱”，监控解决“什么时候发现问题”，配置平台解决“怎么保证环境一致”，工单和资产平台解决“如何留痕与追责”。
考试角度也很爱把这些知识与事件响应、问题管理、变更发布、CMDB、告警平台组合出题。

### 关键知识

#### 1. 运维流程的基本主线

| 流程 | 关注点 | 典型问题 |
| --- | --- | --- |
| 事件管理 | 快速恢复服务 | 故障发生后如何止损 |
| 问题管理 | 找根因、防复发 | 同类故障为什么反复出现 |
| 变更管理 | 控制风险 | 谁批准、何时改、如何回退 |
| 发布管理 | 上线受控 | 版本、窗口、验证、回退 |
| 配置管理 | 保证一致性 | 当前到底是什么版本 |
| 请求管理 | 处理用户申请 | 装软件、开权限、加账号 |

- 事件管理关注“现在出故障了怎么办”。
- 问题管理关注“为什么总是出这个故障”。
- 变更管理关注“还没改的时候，怎样把风险控制住”。
- 发布管理关注“改完以后怎样安全上线”。
- 配置管理关注“上线前后到底哪个版本才是正式版本”。

#### 2. 事件、问题、变更三者的区别

| 概念 | 关键词 | 举例 |
| --- | --- | --- |
| 事件 | 已发生、影响服务 | 用户无法登录、打印服务挂掉 |
| 问题 | 根因、复发、治理 | 域控同步异常导致多次登录失败 |
| 变更 | 即将修改、需审批 | 准备升级补丁、替换证书、改策略 |

- 很多题会把“问题”和“事件”混在一起。
- 简单记忆是：事件偏现象，问题偏根因，变更偏受控调整。
- 桌面运维岗位做得多的是事件处理，但水平真正拉开差距的是问题管理和变更管理。

#### 3. 监控平台的层次化思路

| 监控层次 | 监控对象 | 典型指标 |
| --- | --- | --- |
| 主机层 | CPU、内存、磁盘、网络 | 使用率、I/O、负载、端口 |
| 服务层 | Nginx、Redis、数据库、域控 | 进程状态、连接数、错误率 |
| 应用层 | 接口、登录、工单系统 | 响应时间、成功率、QPS |
| 安全层 | 账号、补丁、病毒、端口暴露 | 异常登录、补丁缺失、查杀告警 |
| 业务层 | 关键功能可用性 | 登录成功率、打印成功率 |

- 单纯监控 CPU 和内存并不等于监控体系成熟。
- 监控应该逐层覆盖，至少要把“资源是否健康、服务是否在线、业务是否可用”串起来。
- 桌面运维考试里，常见问法是“某平台监控哪些指标更有价值”。

#### 4. Prometheus、Grafana、Alertmanager 的组合

| 组件 | 作用 | 说明 |
| --- | --- | --- |
| Prometheus | 采集和存储指标 | Pull 模式为主 |
| Exporter | 暴露指标 | node exporter、windows exporter 等 |
| Alertmanager | 告警路由和抑制 | 发邮件、钉钉、企业微信 |
| Grafana | 可视化看板 | 展示趋势和告警面板 |

- Prometheus 更像“指标数据库”。
- Grafana 更像“图形展示层”。
- Alertmanager 负责把告警送到对的人。
- 题目常爱考“哪个组件采集、哪个组件展示、哪个组件发告警”。

#### 5. 指标、日志、链路的区别

| 类型 | 特点 | 典型问题 |
| --- | --- | --- |
| 指标 | 结构化、可聚合、适合阈值告警 | CPU 高、响应慢 |
| 日志 | 文本丰富、适合排障取证 | 为什么报错、报错堆栈是什么 |
| 链路追踪 | 记录请求经过哪些服务 | 哪一步慢、跨服务调用关系 |

- 桌面运维岗位最常接触的是指标和日志。
- 复杂平台环境下，也会逐渐接触调用链和 APM。
- 考试里如果问“为什么看板正常但用户仍然报慢”，往往就是日志和业务层监控没打通。

#### 6. SLA、SLI、SLO 的理解方式

| 概念 | 解释 |
| --- | --- |
| SLI | 指标本身，例如登录成功率 99.5% |
| SLO | 目标值，例如登录成功率必须大于 99.9% |
| SLA | 对外承诺，例如服务中断超过多久要赔付或升级处理 |

- 这三个概念越来越常见。
- 即便桌面运维考试不会深挖，也适合形成体系化理解。
- 简单记忆是：SLI 是测量，SLO 是目标，SLA 是承诺。

#### 7. CMDB、资产平台、配置中心的边界

| 平台 | 核心职责 | 典型内容 |
| --- | --- | --- |
| CMDB | 记录配置项和关联关系 | 主机、系统、服务、负责人、依赖关系 |
| 资产平台 | 记录设备资产生命周期 | 型号、序列号、采购、领用、报废 |
| 配置中心 | 管理运行参数 | 应用配置、环境变量、开关项 |

- 三者容易混，但不完全相同。
- 资产平台偏“硬件和生命周期”。
- CMDB 偏“配置项和依赖关系”。
- 配置中心偏“应用运行参数”。

#### 8. 工单平台与服务台思维

| 模块 | 用途 | 典型动作 |
| --- | --- | --- |
| 申请单 | 用户提出需求 | 装软件、加权限、开账号 |
| 事件单 | 处理故障 | 登录失败、打印异常 |
| 问题单 | 根因分析 | 追踪多次重复故障 |
| 变更单 | 做受控调整 | 打补丁、改策略、升级系统 |
| 发布单 | 上线新版本 | 窗口审批、回退方案 |

- 工单不是“走形式”，而是标准化和留痕的载体。
- 没有工单体系，后续追踪、审计和 SLA 统计都很困难。

#### 9. 变更和发布为什么一定要联动

- 变更解决“是否允许改”。
- 发布解决“什么时候上线、怎么上线、失败怎么退”。
- 只做变更审批、不做发布控制，容易出现“批准了但上线乱了”。
- 只做发布排期、不做变更审批，容易出现“上线了但没人真正评估风险”。

| 发布策略 | 特点 | 适用场景 |
| --- | --- | --- |
| 蓝绿发布 | 两套环境切换 | 对外系统、回退要求高 |
| 灰度发布 | 先给小部分用户使用 | 风险控制较细 |
| 金丝雀发布 | 小流量验证新版本 | 互联网式应用更常见 |
| 滚动发布 | 分批替换实例 | 容器和服务化环境常见 |

#### 10. 告警治理比“有告警”更重要

| 问题 | 现象 | 后果 |
| --- | --- | --- |
| 告警太多 | 上百条重复告警 | 值班人员麻木 |
| 阈值不合理 | 经常误报或漏报 | 告警失去可信度 |
| 没有抑制 | 同一故障触发多条告警 | 噪音极高 |
| 没有路由 | 告警发错人或没人看 | 处理延迟 |

- 运维成熟度高低，不在于告警数量，而在于告警是否有效、是否可处理、是否能闭环。
- 告警风暴、重复告警、无主告警，是实际工作中很典型的问题。

#### 11. 桌面运维常见平台组合

| 方向 | 常见工具 | 作用 |
| --- | --- | --- |
| 主机监控 | Zabbix、Prometheus | 资源、端口、服务监控 |
| 日志分析 | ELK、Graylog | 日志采集与检索 |
| 跳板管理 | JumpServer 等 | 运维审计和统一入口 |
| 自动化 | Ansible、SaltStack | 批量执行和配置分发 |
| 终端管理 | SCCM、Intune、域控 | 软件分发、策略管理 |

- 不同单位用的具体产品不同，但思路相近。
- 考试里更看重你是否理解“平台解决什么问题”，而不是记所有产品名。

#### 12. 一个完整故障闭环应包含什么

| 步骤 | 说明 |
| --- | --- |
| 发现 | 监控告警或用户报障 |
| 确认 | 判断影响范围和优先级 |
| 处置 | 恢复服务或绕过故障 |
| 通知 | 向相关人同步现状和影响 |
| 复盘 | 分析根因和改进措施 |
| 沉淀 | 更新知识库、流程和告警规则 |

- 真正高质量的运维，不是把故障“压下去”就结束，而是把经验沉淀下来。

### 高频考点

#### 常见概念题

- 事件管理偏快速恢复，问题管理偏根因分析。
- 变更管理是审批与风险控制，发布管理是上线执行与回退控制。
- CMDB、资产平台、配置中心分别管理不同对象。
- Prometheus 负责采集和存储指标，Grafana 负责展示。
- SLI、SLO、SLA 经常组合考。

#### 常见比较题

- 指标适合做阈值与趋势，日志适合做排障与取证。
- 蓝绿、灰度、金丝雀、滚动发布经常从风险和复杂度角度比较。
- 工单平台解决流程留痕，监控平台解决故障发现，两者不能互相替代。
- 事件管理和问题管理既相关又不同。
- 资产管理和配置管理边界不同。

#### 常见场景题

- 监控只有资源指标，没有业务指标，可能会出现“机器正常但用户不可用”。
- 告警没有分级和抑制，容易形成告警噪音。
- 变更单审批通过但无回退方案，属于发布风险未控制。
- 故障解决后不复盘，问题管理就没有真正开展。
- CMDB 长期不更新，后续故障定位和变更评估都会失真。


<h2 id="Nginx">Nginx</h2>

### 基础介绍

Nginx 是高性能 Web 服务器，也常作为反向代理、负载均衡和 HTTPS 入口层。
在桌面运维或平台运维场景中，它通常处在“前门位置”，负责接住用户请求，再把请求转给后端应用。
所以学习 Nginx，不能只会启动和重载，更重要的是看懂配置结构、理解转发路径、定位 4xx 和 5xx 错误，并能做基本性能和安全加固。

### 关键知识

#### 1. 为什么 Nginx 能高并发

| 原因 | 说明 |
| --- | --- |
| 事件驱动 | 用事件模型处理大量连接，而不是一个连接对应一个线程 |
| worker 模型 | 多个 worker 进程并发处理请求 |
| 零拷贝 | `sendfile` 减少用户态和内核态之间复制 |
| 内存占用较低 | 静态资源场景下效率很高 |

- Nginx 的强项是静态资源、反向代理和连接处理能力。
- 它并不是 Java 容器，也不是数据库。
- 考试里常用 Nginx 和 Tomcat 比较本质定位。

#### 2. 配置文件结构必须会看

| 层级 | 作用 |
| --- | --- |
| main | 全局配置，如用户、worker 数 |
| events | 连接模型和连接数 |
| http | HTTP 层公共配置 |
| upstream | 定义后端服务器组 |
| server | 定义虚拟主机 |
| location | 定义路径匹配和处理规则 |

```nginx
user nginx;
worker_processes auto;

events {
    worker_connections 1024;
}

http {
    include mime.types;
    default_type application/octet-stream;

    upstream app_backend {
        server 10.0.0.10:8080;
        server 10.0.0.11:8080;
    }

    server {
        listen 80;
        server_name example.com;
        location / {
            proxy_pass http://app_backend;
        }
    }
}
```

- 读配置时，先看全局，再看 `server`，最后看 `location`。
- 很多排障慢的原因是上来就盯一小段配置，看不出整体链路。

#### 3. location 匹配规则是高频难点

| 写法 | 优先级理解 | 示例 |
| --- | --- | --- |
| `=` | 精确匹配，优先级最高 | `location = /login` |
| `^~` | 前缀匹配，命中后不再走正则 | `location ^~ /static/` |
| `~` | 区分大小写正则 | `location ~ \.php$` |
| `~*` | 不区分大小写正则 | `location ~* \.(jpg|png)$` |
| 普通前缀 | 最长前缀优先 | `location /api/` |

- 精确匹配优先级最高。
- 普通前缀之间，匹配最长者优先。
- 正则匹配和 `^~` 的关系经常出题。
- 配置路径错配是实际工作里非常高频的错误来源。

#### 4. 反向代理不是简单转发

| 指令 | 作用 |
| --- | --- |
| `proxy_pass` | 指定后端地址 |
| `proxy_set_header Host $host` | 传递原始主机名 |
| `proxy_set_header X-Real-IP $remote_addr` | 传递客户端真实 IP |
| `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for` | 传递代理链路 IP |
| `proxy_read_timeout` | 后端读取超时 |
| `proxy_connect_timeout` | 连接后端超时 |

- 如果后端应用需要知道真实来源 IP，就要正确传递头。
- 很多应用日志里只看到代理服务器地址，就是因为头没配对。
- 502、504 问题经常和代理超时、后端端口、后端进程状态有关。

#### 5. upstream 负载均衡需要理解策略差异

| 策略 | 特点 | 场景 |
| --- | --- | --- |
| 轮询 | 默认方式，平均分配 | 大多数普通场景 |
| `least_conn` | 最少连接优先 | 请求处理时长差异大时 |
| `ip_hash` | 同一客户端尽量落到同一后端 | 会话保持场景 |
| `weight` | 按权重分配 | 新老机器性能不一致 |
| `backup` | 主节点异常时启用 | 容灾备用 |

- 负载均衡算法的本质是“怎样把请求更合理地分给后端”。
- 题目常考什么时候需要会话保持，什么时候适合权重调度。

#### 6. HTTPS 与 TLS 基本配置必须懂

| 项目 | 说明 |
| --- | --- |
| 证书文件 | 证明服务端身份 |
| 私钥文件 | 与证书配对，必须严格保护 |
| 协议版本 | 常见配置是 TLSv1.2 与 TLSv1.3 |
| 加密套件 | 决定握手安全等级 |
| 80 跳 443 | 强制用户走 HTTPS |

```nginx
server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate /etc/nginx/ssl/example.com.crt;
    ssl_certificate_key /etc/nginx/ssl/example.com.key;
    ssl_protocols TLSv1.2 TLSv1.3;

    location / {
        proxy_pass http://app_backend;
    }
}
```

- HTTPS 题目里经常把证书、私钥、协议版本、重定向放在一起考。
- 如果用户访问证书报错，排查要从证书链、域名匹配、过期时间、浏览器信任链入手。

#### 7. 静态资源优化与缓存机制

| 技术 | 作用 |
| --- | --- |
| `expires` | 控制浏览器缓存时间 |
| `Cache-Control` | 更细粒度控制缓存 |
| `gzip` | 压缩文本内容，减少传输大小 |
| `sendfile` | 提高文件传输效率 |
| `open_file_cache` | 缓存文件描述信息 |

- 静态资源缓存是 Nginx 非常典型的应用场景。
- 但缓存带来性能的同时，也可能带来“前端资源不刷新”的问题。
- 所以版本化文件名和缓存策略要配套设计。

#### 8. 访问控制与安全加固

| 能力 | 指令或方式 | 目的 |
| --- | --- | --- |
| IP 白名单 | `allow` / `deny` | 限制来源 |
| 基础认证 | `auth_basic` | 提供简单口令保护 |
| 限流 | `limit_req` | 防刷、防突发流量 |
| 限连接 | `limit_conn` | 防止恶意占连接 |
| 隐藏版本 | `server_tokens off` | 减少信息暴露 |

- 安全加固不只是一句“上防火墙”。
- 入口层服务最容易被扫、被探测、被暴力尝试，所以 IP 控制、限流、日志审计都很重要。

#### 9. 日志是排障核心入口

| 日志 | 用途 |
| --- | --- |
| `access.log` | 看谁访问了什么、返回了什么状态码 |
| `error.log` | 看配置错误、代理错误、上游异常 |

| 状态码 | 运维理解 |
| --- | --- |
| 400 | 请求有问题，可能是格式或头异常 |
| 403 | 权限被拒绝 |
| 404 | 路径不存在 |
| 499 | 客户端主动断开 |
| 500 | 服务端内部错误 |
| 502 | 上游服务异常或不可达 |
| 503 | 服务不可用，可能是过载或维护 |
| 504 | 网关超时，上游响应太慢 |

- 499 是 Nginx 场景里比较典型的特殊状态码。
- 502 和 504 经常一起考，但侧重点不同。
- 502 更像“后端不对劲”，504 更像“后端太慢”。

#### 10. 常用命令与操作顺序

| 命令 | 用途 |
| --- | --- |
| `nginx -t` | 检查配置语法 |
| `nginx -s reload` | 平滑重载配置 |
| `systemctl restart nginx` | 重启服务 |
| `ss -tulnp | grep nginx` | 看监听端口 |
| `tail -f access.log` | 跟踪访问日志 |

- 最标准的操作顺序是：改配置 -> `nginx -t` -> `reload`。
- 不做语法检查直接 reload，是非常典型的事故来源。

#### 11. 性能调优的几个抓手

| 参数 | 作用 | 思路 |
| --- | --- | --- |
| `worker_processes` | worker 数量 | 常按 CPU 核数或 auto |
| `worker_connections` | 单 worker 最大连接数 | 结合并发量估算 |
| `keepalive_timeout` | 长连接保持时间 | 平衡性能与资源占用 |
| `client_max_body_size` | 上传大小限制 | 解决大文件上传失败 |
| `proxy_read_timeout` | 后端读取超时 | 长请求场景常见 |

- 性能调优必须结合业务，不是所有参数越大越好。
- 连接数、文件句柄、后端能力、系统内核参数都可能成为瓶颈。

#### 12. 一条标准排障思路

1. 先看服务是否存活。
2. 再看监听端口是否在。
3. 再看 `nginx -t` 是否通过。
4. 再看 access 和 error 日志。
5. 如果是代理场景，再验证上游应用是否正常。
6. 如果是 HTTPS 场景，再查证书和域名。
7. 如果是性能问题，再看连接数、响应时延和后端处理能力。

### 高频考点

#### 常见概念题

- Nginx 是高性能 Web 服务器和反向代理，不是 Java 容器。
- `server` 管虚拟主机，`location` 管路径规则。
- `nginx -t` 是语法检查命令。
- `proxy_pass` 是反向代理核心指令。
- `access.log` 和 `error.log` 分工不同。

#### 常见比较题

- Nginx 更强在静态资源和代理，Tomcat 更强在 Java Web 容器。
- 502 与 504 不是一回事。
- 轮询、`least_conn`、`ip_hash` 的适用场景不同。
- `=`、`^~`、`~`、普通前缀的匹配逻辑经常一起考。
- HTTPS 不只是开 443，还包括证书、协议和跳转策略。

#### 常见场景题

- 后端服务挂掉但 Nginx 还在，会出现 502 或 504。
- 上传大文件报错，常和 `client_max_body_size` 有关。
- 访问后台管理页只允许内网访问，适合做 IP 白名单控制。
- 切证书后浏览器仍报错，要考虑域名和证书链问题。
- 配完缓存后前端页面不刷新，往往是缓存策略没有配合版本控制。


<h2 id="Redis">Redis</h2>

### 基础介绍

Redis 是典型的内存型键值数据库，也可做持久化。
它常用于缓存、会话、计数器、排行榜、分布式锁和轻量消息场景。
Redis 的学习重点不只是会用几条命令，而是要理解它为什么快、什么时候适合用、什么时候不适合用，以及出了问题之后怎么判断是内存、持久化、网络还是数据模型的问题。

### 关键知识

#### 1. Redis 的定位与优势

| 维度 | 说明 |
| --- | --- |
| 数据存储方式 | 以内存为主，速度快 |
| 数据模型 | 键值为核心，但值支持多种结构 |
| 读写延迟 | 通常可做到毫秒甚至亚毫秒级 |
| 高可用能力 | 支持主从、哨兵、集群 |

- Redis 不是关系型数据库，不擅长复杂关联查询。
- 它最大的价值是“快”和“结构简单灵活”。
- 考试里常考为什么缓存会选 Redis，而不是直接把所有请求都打到 MySQL。

#### 2. 为什么 Redis 快

| 原因 | 说明 |
| --- | --- |
| 内存读写 | 内存比磁盘快很多 |
| 数据结构简单 | 操作成本低 |
| 单线程命令执行模型 | 避免大量锁竞争 |
| I/O 多路复用 | 高效处理大量连接 |

- “单线程”不等于性能差。
- 在内存数据库场景里，线程切换和锁竞争反而可能是额外开销。
- Redis 6 以后 I/O 层也引入了多线程能力，但核心命令执行仍保持有序模型。

#### 3. 常见数据结构与场景映射

| 类型 | 说明 | 典型场景 |
| --- | --- | --- |
| String | 最基础类型 | 缓存值、计数器、令牌 |
| Hash | 键下再存字段 | 用户信息、资产属性 |
| List | 有序列表 | 队列、消息缓冲 |
| Set | 无序去重集合 | 标签、用户去重 |
| ZSet | 带分值的有序集合 | 排行榜、延时任务 |
| Bitmap | 位图 | 签到、活跃用户标记 |
| HyperLogLog | 基数估算 | UV 估算 |
| Stream | 流式消息结构 | 轻量消息流 |

- 数据结构题是 Redis 高频基础题。
- 不是所有东西都用 String。
- 会按场景选结构，比死记命令更重要。

#### 4. 常用命令一定要分场景记

| 场景 | 常见命令 |
| --- | --- |
| 连接与状态 | `redis-cli ping`、`info`、`client list` |
| String | `set`、`get`、`incr` |
| Hash | `hset`、`hgetall` |
| List | `lpush`、`rpop` |
| Set | `sadd`、`smembers` |
| ZSet | `zadd`、`zrange` |
| Key 管理 | `ttl`、`expire`、`scan` |

- 运维视角里，`ttl`、`expire`、`info`、`scan` 这些命令特别常用。
- `keys *` 在生产环境高风险，经常被当作错误选项考。

#### 5. 持久化：RDB、AOF、混合模式

| 方式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| RDB | 定时生成数据快照 | 文件紧凑、恢复快 | 可能丢失最近一次快照后的数据 |
| AOF | 记录写命令日志 | 数据更完整 | 文件更大、恢复较慢 |
| 混合持久化 | RDB + AOF 结合 | 平衡恢复速度与数据完整性 | 配置更复杂 |

- RDB 像“拍照片”。
- AOF 像“记流水”。
- 考试经常把二者的取舍和故障恢复放在一起考。

#### 6. 内存管理与淘汰策略

| 配置 | 含义 |
| --- | --- |
| `maxmemory` | 允许 Redis 使用的最大内存 |
| `maxmemory-policy` | 达到上限时的淘汰策略 |

| 淘汰策略 | 说明 |
| --- | --- |
| `noeviction` | 不淘汰，写请求报错 |
| `allkeys-lru` | 所有 key 中淘汰最近最少使用 |
| `volatile-lru` | 只在设置了过期时间的 key 中淘汰 |
| `allkeys-random` | 所有 key 中随机淘汰 |
| `volatile-ttl` | 优先淘汰即将过期的 key |

- 如果用 Redis 做缓存，不配置过期策略和内存上限，极容易把宿主机拖垮。
- 内存淘汰策略经常作为概念题出现。

#### 7. 主从复制、哨兵、集群的层次关系

| 模式 | 解决的问题 |
| --- | --- |
| 主从复制 | 提供读扩展和基础冗余 |
| Sentinel | 监控主从并自动切换主节点 |
| Cluster | 做水平扩展和分片 |

- 主从复制解决不了真正的自动故障切换问题，所以才有哨兵。
- 哨兵解决高可用，不等于解决海量数据水平扩容。
- 集群解决的是分片扩展和部分高可用。

#### 8. Redis 常见故障和风险点

| 问题 | 说明 | 影响 |
| --- | --- | --- |
| 热 key | 某个 key 被高频访问 | 单点压力过高 |
| 大 key | 一个 key 下数据过大 | 删除慢、迁移慢、阻塞 |
| 缓存穿透 | 请求大量打到不存在的数据 | 后端被打穿 |
| 缓存击穿 | 热点 key 恰好过期 | 瞬时打爆数据库 |
| 缓存雪崩 | 大量 key 同时过期 | 后端瞬时压力过大 |

- 这些概念非常适合做考试题。
- 解决思路一般包括过期时间随机化、热点预热、空值缓存、布隆过滤器、互斥锁等。

#### 9. 事务、Pipeline、Lua 的边界

| 技术 | 用途 | 特点 |
| --- | --- | --- |
| Pipeline | 批量发送命令减少往返 | 提高吞吐，不保证事务性 |
| `MULTI/EXEC` | Redis 事务 | 顺序执行，但不如传统数据库事务 |
| Lua 脚本 | 把多步逻辑放进一个原子脚本 | 适合分布式锁和复杂原子操作 |

- Pipeline 和事务经常被混淆。
- Pipeline 关注的是性能，事务关注的是一组命令顺序提交。
- Lua 脚本常用于避免多条命令之间的竞态条件。

#### 10. 安全配置不能忽视

| 项目 | 说明 |
| --- | --- |
| `bind` | 绑定监听地址 |
| `protected-mode` | 保护模式 |
| `requirepass` 或 ACL | 设置访问控制 |
| 防火墙 | 限制来源 IP |
| 禁止公网裸露 | Redis 默认端口对外暴露风险极高 |

- Redis 未授权访问是经典安全事故场景。
- 生产环境不应该让 Redis 直接暴露在公网。
- “只设置密码、不设防火墙”和“只设防火墙、不设认证”都不够稳妥。

#### 11. 运维排障常看哪些信息

| 命令 | 作用 |
| --- | --- |
| `info memory` | 看内存使用 |
| `info replication` | 看主从复制状态 |
| `info stats` | 看命中率和连接统计 |
| `slowlog get` | 看慢命令 |
| `latency doctor` | 看延迟问题 |
| `scan` | 安全遍历 key |

- 命中率低不一定是 Redis 问题，也可能是业务缓存策略不合理。
- 慢命令不一定是 CPU 问题，也可能是大 key、删除大集合、网络拥堵等原因。

#### 12. Redis 与 MySQL 的分工边界

| 维度 | Redis | MySQL |
| --- | --- | --- |
| 存储介质 | 内存为主 | 磁盘为主 |
| 查询模型 | 键值和简单结构 | 关系型 SQL |
| 延迟 | 很低 | 相对更高 |
| 持久化能力 | 有，但不是强关系型替代 | 强 |
| 典型用途 | 缓存、计数、会话、排行榜 | 核心数据持久化 |

- Redis 经常是数据库前面的加速层，而不是把关系库完全替掉。

### 高频考点

#### 常见概念题

- Redis 是 NoSQL 中的键值数据库。
- RDB 是快照，AOF 是追加日志。
- 主从复制、哨兵、集群的职责不同。
- String、Hash、List、Set、ZSet 的场景要分清。
- `scan` 比 `keys *` 更适合生产环境。

#### 常见比较题

- 热 key 与大 key 的问题性质不同。
- Pipeline 解决性能，事务和 Lua 更偏原子性。
- 哨兵解决高可用，集群解决扩容与分片。
- Redis 和 MySQL 是协作关系，不是简单替代关系。
- `allkeys-lru` 与 `volatile-lru` 的淘汰范围不同。

#### 常见场景题

- 大量 key 同时过期导致数据库压力暴涨，是缓存雪崩。
- 热点 key 过期瞬间大量请求打到数据库，是缓存击穿。
- 请求的 key 本来就不存在，大量绕过缓存打库，是缓存穿透。
- Redis 占满内存却没配淘汰策略，写请求可能失败。
- Redis 对公网暴露且无 ACL、防火墙、密码，是高危配置。


<h2 id="Tomcat">Tomcat</h2>

### 基础介绍

Tomcat 是轻量级 Java Web 容器，主要负责运行 Servlet、JSP 和基于 Java 的 Web 应用。
对桌面运维或平台运维来说，它最常出现的场景是作为后端应用容器，被 Nginx 放在前面做代理入口。
考试重点不在开发细节，而在目录结构、部署方式、端口、日志、JVM 参数和常见故障定位。

### 关键知识

#### 1. Tomcat 的基本定位

| 维度 | 说明 |
| --- | --- |
| 本质 | Java Web 容器 |
| 核心能力 | 运行 Servlet、JSP |
| 常见部署方式 | 部署 WAR 包 |
| 常见组合 | Nginx + Tomcat |

- Tomcat 不是通用 Web 代理。
- 它更偏应用运行容器，而不是入口层代理。

#### 2. 目录结构必须会认

| 目录 | 作用 |
| --- | --- |
| `bin` | 启停脚本 |
| `conf` | 配置文件 |
| `logs` | 日志文件 |
| `webapps` | 应用部署目录 |
| `temp` | 临时文件 |
| `work` | 编译后的 JSP 等缓存 |

- 排障时，目录结构能让你快速找到脚本、配置和日志。

#### 3. 常见配置文件

| 文件 | 用途 |
| --- | --- |
| `server.xml` | 主配置，端口、连接器、虚拟主机 |
| `web.xml` | 应用默认配置 |
| `context.xml` | 上下文和资源配置 |
| `catalina.properties` | 类加载、通用属性 |

#### 4. 连接器与端口

| 端口 | 说明 |
| --- | --- |
| 8080 | HTTP 访问端口 |
| 8005 | Shutdown 端口 |
| 8009 | AJP 端口，某些环境会禁用 |

- 端口冲突是启动失败的常见原因。
- AJP 因安全原因在很多环境里不建议随意开放。

#### 5. 日志和常见问题

| 日志 | 说明 |
| --- | --- |
| `catalina.out` | 启动和运行总日志 |
| 应用日志 | 由具体框架输出 |
| GC 日志 | 分析内存回收问题 |

- 应用打不开时，不要只看浏览器报错，要先看 Tomcat 日志。
- 很多“页面 500”并不是 Tomcat 本身挂了，而是应用抛异常。

#### 6. JVM 与性能关注点

| 参数 | 作用 |
| --- | --- |
| `-Xms` | 初始堆内存 |
| `-Xmx` | 最大堆内存 |
| `-Xss` | 线程栈大小 |
| GC 相关参数 | 控制垃圾回收行为 |

- Tomcat 性能问题经常不是“Tomcat 不行”，而是 JVM 内存和应用线程池设置不合理。

#### 7. 常见故障排查思路

1. 看 Java 是否正常。
2. 看 Tomcat 进程是否在。
3. 看端口是否监听。
4. 看日志是否报端口冲突、类缺失、内存不足。
5. 看 Nginx 到 Tomcat 的代理链路是否正常。

### 高频考点

- Tomcat 是 Java Web 容器，不是 Nginx 那样的高性能入口代理。
- `webapps`、`conf`、`logs` 是高频目录。
- 启动失败先看日志和端口冲突。
- Nginx + Tomcat 组合题很常见。
- JVM 参数经常与性能和内存溢出题一起出现。

<h2 id="数据库基础">数据库基础</h2>

### 基础介绍

数据库基础部分是整份资料里最容易被压缩过度、但又最适合拉开难度的章节之一。
桌面运维工程师不一定直接做 DBA，但必须看得懂 SQL、知道索引和事务意味着什么、理解锁和备份恢复的风险、能读一些执行计划和监控指标。
很多考试题本质都不在考“写复杂 SQL”，而在考你是否理解数据库为什么慢、为什么锁住、为什么会丢数据、为什么恢复困难。

### 关键知识

#### 1. 关系型数据库与 NoSQL 的边界

| 维度 | 关系型数据库 | NoSQL |
| --- | --- | --- |
| 数据结构 | 表、行、列 | 键值、文档、列族、图 |
| 查询方式 | SQL | 各自 API 或查询语言 |
| 事务能力 | 强 | 因产品而异 |
| 典型场景 | 核心业务数据 | 缓存、内容、日志、图关系 |

- 关系库擅长强一致和复杂查询。
- NoSQL 擅长灵活结构和高并发特定场景。
- 面试和考试都常问“什么时候用 MySQL，什么时候用 Redis/MongoDB”。

#### 2. SQL 分类必须会分

| 类型 | 作用 | 常见命令 |
| --- | --- | --- |
| DDL | 管理结构 | `CREATE`、`ALTER`、`DROP` |
| DML | 管理数据 | `INSERT`、`UPDATE`、`DELETE` |
| DQL | 查询数据 | `SELECT` |
| DCL | 管理权限 | `GRANT`、`REVOKE` |
| TCL | 管理事务 | `COMMIT`、`ROLLBACK` |

- DDL 与 DML 的区别是高频送分题。
- 很多数据库中，DDL 往往会触发隐式提交，这也是容易被忽视的点。

#### 3. JOIN 不只是语法题，而是数据理解题

| JOIN 类型 | 含义 | 场景 |
| --- | --- | --- |
| INNER JOIN | 只保留两边匹配数据 | 精确关联 |
| LEFT JOIN | 保留左表全部数据 | 主表带辅助信息 |
| RIGHT JOIN | 保留右表全部数据 | 实际较少使用 |
| FULL JOIN | 保留两边未匹配数据 | 完整性检查 |
| CROSS JOIN | 笛卡尔积 | 组合测试 |

- JOIN 题本质在于“哪张表的数据一定保留”。
- LEFT JOIN 是业务题里最常见的写法。
- 如果连接字段无索引，JOIN 很容易拖慢查询。

#### 4. 索引为什么快

| 角度 | 说明 |
| --- | --- |
| 本质 | 用空间换时间 |
| 作用 | 减少扫描范围 |
| 常见结构 | B+Tree 为主 |
| 代价 | 写入变慢，占空间 |

- 索引像书的目录。
- 没索引时，数据库更像一页页翻书。
- 有索引时，可以更快定位数据范围。

#### 5. 索引常见类型与策略

| 类型 | 说明 | 场景 |
| --- | --- | --- |
| 主键索引 | 唯一标识行 | 主键查询 |
| 唯一索引 | 保证列值唯一 | 账号、手机号 |
| 普通索引 | 提高查询效率 | 普通查询条件 |
| 复合索引 | 多列一起建索引 | 多条件组合查询 |
| 覆盖索引 | 查询字段都在索引里 | 减少回表 |

- 复合索引的最左前缀原则是高频重点。
- 不是字段越多越好，也不是所有字段都值得建索引。
- 低选择性字段单独建索引往往收益不大。

#### 6. 什么情况下索引会失效

| 场景 | 原因 |
| --- | --- |
| 对列做函数计算 | 破坏原索引有序性 |
| 隐式类型转换 | 优化器可能无法正确使用索引 |
| `%abc` 前置模糊匹配 | 无法走普通 B+Tree 前缀匹配 |
| 复合索引跳过最左列 | 不满足最左前缀原则 |
| 查询列过多回表成本高 | 优化器可能选择全表扫描 |

- 索引失效题特别适合作为稍有难度的选择题或场景题。
- `where year(create_time)=2024` 这类写法就是经典反例。

#### 7. 事务 ACID 要理解到位

| 特性 | 含义 |
| --- | --- |
| Atomicity 原子性 | 要么全做，要么全不做 |
| Consistency 一致性 | 事务前后满足规则约束 |
| Isolation 隔离性 | 并发事务互不干扰 |
| Durability 持久性 | 提交后结果不会轻易丢失 |

- ACID 是数据库题的核心主线之一。
- 原子性经常和回滚、Undo 关联。
- 持久性经常和 Redo、日志刷盘关联。

#### 8. 并发现象与隔离级别

| 问题 | 解释 |
| --- | --- |
| 脏读 | 读到别人未提交的数据 |
| 不可重复读 | 同一行前后两次读取结果不同 |
| 幻读 | 同一条件前后两次查询结果集条数不同 |

| 隔离级别 | 能否避免脏读 | 能否避免不可重复读 | 能否避免幻读 |
| --- | --- | --- | --- |
| 读未提交 | 否 | 否 | 否 |
| 读已提交 | 是 | 否 | 否 |
| 可重复读 | 是 | 是 | 视实现而定 |
| 串行化 | 是 | 是 | 是 |

- 这组概念是数据库考试最经典的必考内容。
- 记忆时要用“现象”去对应，而不是只背名字。

#### 9. MVCC 为什么常被提到

- MVCC 是多版本并发控制。
- 它的目标是减少读写冲突，让读操作可以看到某个一致性快照。
- 这就是为什么在很多数据库里，读已提交和可重复读可以在不全靠加锁的情况下运行。

#### 10. 锁的类型和风险

| 锁 | 用途 |
| --- | --- |
| 共享锁 | 读时使用，允许并发读 |
| 排他锁 | 写时使用，阻止其他读写或写 |
| 行锁 | 锁定某一行 | 并发高，影响小 |
| 表锁 | 锁定整张表 | 影响大 |

- “为什么同一条 SQL 会把业务拖慢”很多时候就是锁等待问题。
- 无索引更新容易把行锁放大成更重的锁冲突。

#### 11. 死锁是如何产生的

```text
事务 A 占有资源 1，等待资源 2。
事务 B 占有资源 2，等待资源 1。
彼此都等，就形成死锁。
```

- 预防思路通常是统一访问顺序、缩短事务、尽早提交、命中索引。
- 死锁题经常和锁顺序、事务时长一起出。

#### 12. 表结构设计与范式

| 范式 | 核心思想 |
| --- | --- |
| 1NF | 字段原子化 |
| 2NF | 消除对组合主键的部分依赖 |
| 3NF | 消除传递依赖 |

- 范式是“减少冗余和异常”的设计原则。
- 但在真实系统里，也会为了性能适当做反范式设计。
- 所以范式题要理解“设计目标”和“性能取舍”。

#### 13. SQL 优化的几个通用原则

| 原则 | 说明 |
| --- | --- |
| 只查需要的列 | 避免 `select *` |
| 命中索引 | where、join、order by 结合索引 |
| 尽量少回表 | 设计覆盖索引 |
| 避免大偏移分页 | 用主键范围分页更稳 |
| 小表驱动大表 | 减少无效扫描 |

- SQL 优化题常喜欢给出“看起来能跑，但很慢”的 SQL，让你找出问题所在。

#### 14. 审计、监控和备份是运维视角重点

| 方向 | 常见内容 |
| --- | --- |
| 审计 | 登录、查询、结构变更、权限变更 |
| 监控 | QPS、慢 SQL、连接数、锁等待、磁盘空间 |
| 备份 | 全量、增量、逻辑备份、物理备份 |

- 只会查数据不够，运维更关注“出了问题能不能定位，数据坏了能不能恢复”。

#### 15. 逻辑备份与物理备份的区别

| 类型 | 特点 | 场景 |
| --- | --- | --- |
| 逻辑备份 | 导出 SQL 或对象定义 | 迁移、单表恢复、跨版本 |
| 物理备份 | 直接备份数据文件或页块 | 快速恢复、大库备份 |

- 逻辑备份灵活，但恢复大库较慢。
- 物理备份恢复快，但与引擎和版本耦合更紧。

#### 16. 一张数据库排障的思路表

| 现象 | 首先看什么 |
| --- | --- |
| 查询慢 | 执行计划、索引、是否回表 |
| 系统卡 | 锁等待、长事务、死锁 |
| CPU 高 | 全表扫描、复杂排序、统计缺失 |
| 磁盘满 | 日志、备份文件、归档 |
| 连接异常 | 连接数、网络、认证、监听 |

### 高频考点

#### 常见概念题

- DDL、DML、DQL、DCL、TCL 的分类必须分清。
- ACID 是数据库事务核心。
- 脏读、不可重复读、幻读是并发经典概念。
- 主键索引、唯一索引、复合索引的作用不同。
- 逻辑备份和物理备份的场景不同。

#### 常见比较题

- LEFT JOIN 与 INNER JOIN 的保留数据范围不同。
- RDBMS 与 NoSQL 的定位不同。
- 行锁与表锁的影响范围不同。
- 逻辑备份灵活，物理备份恢复快。
- 索引提高查询速度，但会增加写入成本。

#### 常见场景题

- 查询很慢但数据量不大，可能是索引失效或回表太多。
- 更新语句长时间不返回，可能是锁等待。
- `select *`、函数包裹字段、前置 `%` 模糊查询，都可能让 SQL 变慢。
- 大量重复故障不只是事件处理问题，更需要问题管理和审计分析。
- 备份做了但恢复演练从不做，真实出事时仍可能恢复失败。


<h2 id="Oracle">Oracle</h2>

### 基础介绍

Oracle 是企业级关系型数据库的代表，在金融、政务、电信等对稳定性和功能完整性要求很高的场景中长期占据重要位置。
对运维考试来说，Oracle 的难点不只是名词多，而是它有一整套自身语境：实例、表空间、REDO、UNDO、归档、RMAN、RAC、Data Guard、多租户等。
真正掌握 Oracle，不是把所有术语背下来，而是能把“架构、恢复、高可用、排障”几条主线串起来。

### 关键知识

#### 1. 实例与数据库不是一回事

| 概念 | 含义 |
| --- | --- |
| 实例 | 内存结构 + 后台进程 |
| 数据库 | 数据文件、控制文件、日志文件等持久化文件集合 |

- 实例负责“运行时处理”。
- 数据库负责“数据长期存放”。
- 这组概念是 Oracle 的入门必考点。

#### 2. SGA、PGA 与后台进程

| 组件 | 作用 |
| --- | --- |
| SGA | 共享内存区，多个会话共享 |
| PGA | 进程私有内存 |
| DBWn | 把缓冲区数据写回数据文件 |
| LGWR | 写重做日志 |
| SMON | 实例恢复 |
| PMON | 进程清理和会话恢复 |

- Oracle 的性能和恢复题，很多都围绕这些组件展开。

#### 3. Oracle 启动状态要会区分

| 状态 | 含义 |
| --- | --- |
| NOMOUNT | 实例启动，但未关联数据库文件 |
| MOUNT | 已加载控制文件 |
| OPEN | 数据库正式可用 |

```sql
STARTUP NOMOUNT;
ALTER DATABASE MOUNT;
ALTER DATABASE OPEN;
```

- 启动状态经常和恢复场景放在一起考。

#### 4. 表空间与数据文件

| 概念 | 解释 |
| --- | --- |
| 表空间 | 逻辑存储单位 |
| 数据文件 | 物理存储文件 |
| 段 | 对象占用的一组区 |
| 区 | 连续的数据块集合 |
| 数据块 | Oracle 最小 I/O 单位 |

- 表空间是逻辑概念，数据文件是物理概念。
- 这组关系题是 Oracle 高频基础知识。

#### 5. 会话、监听与服务名

| 术语 | 运维理解 |
| --- | --- |
| Session | 用户连接后的逻辑会话 |
| Listener | 接收客户端连接请求 |
| TNS 服务名 | 客户端访问数据库的逻辑名称 |

- 连接不上 Oracle，很多时候不是数据库宕机，而是监听、网络、服务名配置或认证问题。

#### 6. REDO 与 UNDO 的区别必须吃透

| 项目 | REDO | UNDO |
| --- | --- | --- |
| 目标 | 保证持久性 | 支持回滚和一致性读 |
| 内容 | 写入变化记录 | 修改前旧数据 |
| 场景 | 故障恢复 | 回滚、MVCC |

- REDO 像“做了什么”。
- UNDO 像“原来是什么”。
- 这是 Oracle 和事务恢复题的核心主线。

#### 7. 归档模式与恢复能力

| 模式 | 特点 |
| --- | --- |
| NOARCHIVELOG | 重做日志循环覆盖，恢复能力有限 |
| ARCHIVELOG | 保留归档日志，支持更完整恢复 |

- 生产环境一般要求归档模式。
- 没有归档日志，很多时间点恢复就做不到。

#### 8. RMAN 的位置

| 能力 | 说明 |
| --- | --- |
| 全库备份恢复 | 快速恢复数据库 |
| 表空间恢复 | 精细恢复 |
| 数据文件恢复 | 定位具体文件 |
| 时间点恢复 | 恢复到误操作前 |

- RMAN 是 Oracle 备份恢复的标准工具。
- 内部考试常把 RMAN 和 Data Pump 做对比。

#### 9. Data Pump 与 RMAN 的差异

| 工具 | 本质 | 适合场景 |
| --- | --- | --- |
| RMAN | 物理备份恢复 | 灾难恢复、大规模快速恢复 |
| expdp/impdp | 逻辑导入导出 | 迁移、对象级导出导入 |

- 这两个工具不是替代关系，而是解决不同问题。

#### 10. 多租户 CDB/PDB

| 概念 | 解释 |
| --- | --- |
| CDB | 容器数据库 |
| PDB | 可插拔数据库，类似租户 |

- 从 12c 开始，多租户是 Oracle 很重要的架构演进方向。
- 考试里常用它来考“容器与租户”的概念边界。

#### 11. RAC 与 Data Guard 的侧重点不同

| 技术 | 重点 |
| --- | --- |
| RAC | 多实例共享存储，高可用与扩展 |
| Data Guard | 主备复制与容灾 |

- RAC 更偏同城或本地集群高可用。
- DG 更偏主备和异地容灾。
- 很多题目喜欢考“哪个解决集群可用，哪个解决容灾”。

#### 12. AWR、ASH 与性能诊断

| 工具 | 作用 |
| --- | --- |
| AWR | 自动工作负载报告，偏整体性能历史 |
| ASH | 活动会话历史，偏会话级分析 |

- Oracle 的性能诊断题常把这两个缩写放在一起考。

#### 13. 常见运维风险点

| 风险 | 说明 |
| --- | --- |
| 归档目录满 | 导致数据库受影响 |
| 表空间满 | 业务写入失败 |
| 监听异常 | 客户端无法连接 |
| 长事务 | 影响锁和 Undo |
| 备份不验证 | 真正恢复时可能失败 |

### 高频考点

- 实例与数据库的区别。
- SGA、PGA、DBWn、LGWR 的作用。
- REDO 与 UNDO 的区别。
- ARCHIVELOG 与 NOARCHIVELOG 的恢复能力差异。
- RMAN 和 Data Pump 的差异。
- CDB/PDB、多租户、RAC、DG 这些词的定位。


<h2 id="Mysql">Mysql</h2>

### 基础介绍

MySQL 是最常见的开源关系型数据库之一，互联网系统和企业内部系统里都大量使用。
对桌面运维工程师来说，MySQL 相关知识的重点并不是“把每条 SQL 写得多花”，而是知道存储引擎、事务、索引、日志、复制和备份这些东西在运维中意味着什么。
当业务说“系统慢”“数据库连不上”“主从延迟大”“导数据失败”时，你至少要有一套基本判断框架。

### 关键知识

#### 1. MySQL 架构分层

| 层次 | 作用 |
| --- | --- |
| 连接层 | 接收客户端连接、认证 |
| SQL 层 | 解析、优化、执行 SQL |
| 存储引擎层 | 真正存取数据 |
| 文件系统层 | 数据文件和日志文件 |

- MySQL 不是只有“一个进程 + 一个数据文件”这么简单。
- SQL 优化和存储引擎问题往往不在同一层。

#### 2. InnoDB 是重点中的重点

| 特性 | 说明 |
| --- | --- |
| 支持事务 | 是 |
| 支持行锁 | 是 |
| 支持 MVCC | 是 |
| 支持外键 | 是 |

- 现在大多数生产环境默认重点都在 InnoDB。
- 所以内部考试如果问 MySQL 引擎，通常是以 InnoDB 为主语境。

#### 3. Buffer Pool、Redo、Undo、Binlog 的分工

| 组件 | 作用 |
| --- | --- |
| Buffer Pool | 缓存热点数据页 |
| Redo Log | 保证已提交事务持久性 |
| Undo Log | 回滚和一致性读 |
| Binlog | 记录逻辑变更，用于复制和恢复 |

- 这几个概念经常被放在一题里一起考。
- 简单理解是：Buffer Pool 管性能，Redo/Undo 管事务，Binlog 管复制和恢复。

#### 4. 索引与执行计划

| 工具 | 作用 |
| --- | --- |
| `EXPLAIN` | 看 SQL 的执行计划 |
| `SHOW INDEX` | 看表上索引 |
| 慢查询日志 | 发现慢 SQL |

- `EXPLAIN` 是 SQL 排障非常重要的入口。
- 如果题目问“如何初步分析一条慢 SQL”，高概率会提到执行计划。

#### 5. 锁与事务风险

| 现象 | 可能原因 |
| --- | --- |
| 更新卡住 | 行锁等待或事务未提交 |
| 死锁 | 两个事务交叉等待资源 |
| 数据不一致 | 事务边界设计不合理 |

- MySQL 的锁问题和数据库基础章节是互通的。
- 但在 MySQL 场景里，更常直接通过 `SHOW ENGINE INNODB STATUS` 辅助诊断。

#### 6. 主从复制与高可用

| 技术 | 作用 |
| --- | --- |
| 主从复制 | 数据同步、读扩展 |
| 半同步复制 | 降低主从数据丢失风险 |
| MGR | 组复制，增强高可用 |

- 主从复制是 MySQL 运维最常见的话题之一。
- 主从延迟、复制中断、主库写压力大，都是典型考点。

#### 7. 常见备份方式

| 工具 | 类型 | 场景 |
| --- | --- | --- |
| `mysqldump` | 逻辑备份 | 中小规模导出 |
| 物理备份工具 | 物理备份 | 大库快速恢复 |
| Binlog | 增量逻辑日志 | 时间点恢复 |

- 只做全量备份不保留 Binlog，恢复粒度会很粗。

#### 8. 常见问题与排障角度

| 问题 | 优先检查 |
| --- | --- |
| 连接失败 | 端口、账号、权限、网络 |
| 查询慢 | 索引、执行计划、慢日志 |
| 主从延迟 | 从库负载、网络、长事务 |
| 磁盘涨满 | Binlog、慢日志、备份 |
| 内存压力大 | Buffer Pool 配置 |

### 高频考点

- InnoDB 是主流引擎。
- Buffer Pool、Redo、Undo、Binlog 的作用要分清。
- `EXPLAIN`、慢查询日志、`SHOW ENGINE INNODB STATUS` 是高频工具。
- 主从复制和 Binlog 常一起出现。
- 备份恢复题常考全量、增量和时间点恢复的组合思路。


<h2 id="国产改造">国产改造</h2>

### 基础介绍

国产改造并不是简单地把一套国外产品换成国产产品。
它通常意味着数据库、中间件、操作系统、CPU、办公终端、安全产品、运维工具链都可能发生变化。
所以国产改造的难点不只在技术选型，更在兼容性验证、迁移窗口、回退方案、人员培训和运维体系重建。

### 关键知识

#### 1. 国产改造一般改什么

| 领域 | 典型内容 |
| --- | --- |
| 操作系统 | Kylin、UOS 等 |
| 数据库 | OceanBase、GoldenDB、达梦、人大金仓等 |
| 中间件 | TongWeb 等 |
| 终端 | 国产 PC、打印外设、浏览器兼容 |
| CPU 与服务器 | 鲲鹏、飞腾、海光等生态 |

#### 2. 为什么国产改造难

- 旧应用往往写死依赖。
- 驱动、字符集、SQL 方言可能不兼容。
- 中间件和数据库链路一变，上层应用也可能要跟着改。
- 终端插件、浏览器控件、打印组件经常是隐蔽问题源。

#### 3. 国产改造的基本阶段

| 阶段 | 重点 |
| --- | --- |
| 现状摸底 | 统计资产、依赖、接口、账号、版本 |
| 兼容性评估 | 找出必须改造的点 |
| 环境搭建 | 先建验证环境 |
| 数据迁移 | 全量、增量、校验 |
| 联调验证 | 业务流程全链路跑通 |
| 切换上线 | 控制窗口、准备回退 |

#### 4. 数据库替换时常见关注点

| 关注点 | 说明 |
| --- | --- |
| SQL 兼容性 | 函数、分页、语法、存储过程 |
| 驱动兼容性 | JDBC/ODBC 是否匹配 |
| 字符集 | 中文、排序规则 |
| 性能表现 | 查询计划、索引命中 |
| 高可用能力 | 主备、分布式、一致性 |

#### 5. 中间件替换时常见关注点

- JDK 版本是否匹配。
- WAR 包部署方式是否一致。
- 集群和会话保持机制是否变化。
- 控制台和监控方式是否不同。

#### 6. 终端与浏览器兼容问题经常被低估

| 风险点 | 说明 |
| --- | --- |
| 浏览器控件 | 旧系统可能依赖 ActiveX 或老插件 |
| 驱动问题 | 打印机、读卡器、扫描枪 |
| 字体与排版 | 国产系统和旧模板可能出现差异 |
| Office 宏 | 文档处理流程可能受影响 |

#### 7. 回退方案是国产改造成败关键之一

- 迁移前必须回答：切不过去怎么办。
- 数据是否双写或可回补。
- DNS、连接串、服务入口如何恢复。
- 谁在什么时间点做回退决策。

### 高频考点

- 国产改造是体系性工程，不是单一产品替换。
- 兼容性评估、联调验证、数据校验、回退方案是关键词。
- 数据库和中间件替换都要关注驱动、语法、监控和运维方式。
- 终端兼容、浏览器插件、驱动适配非常容易出现场景题。


<h2 id="VMWare/FC">VMWare/FC</h2>

### 基础介绍

VMware 代表虚拟化平台能力，FC 一般指 Fibre Channel 光纤通道存储网络。
这部分知识的共同点在于“基础设施层”，也就是计算、网络、存储如何抽象成可管理资源。
在企业环境里，虚拟化和 SAN 存储经常一起出现，因为它们共同支撑服务器资源池化、快照、迁移和高可用。

### 关键知识

#### 1. 虚拟化的基本收益

| 价值 | 说明 |
| --- | --- |
| 资源整合 | 一台物理机跑多台虚拟机 |
| 快速交付 | 模板、克隆、快照 |
| 管理集中 | 统一看计算、网络、存储 |
| 高可用 | 宿主机故障可迁移或恢复 |

#### 2. 常见网络模式

| 模式 | 特点 | 场景 |
| --- | --- | --- |
| 桥接 | 虚拟机像局域网独立主机 | 对外提供服务 |
| NAT | 通过宿主机共享上网 | 开发测试 |
| 仅主机 | 只和宿主机及内部网络通信 | 隔离实验 |

- 这部分是虚拟网络的基础送分点。

#### 3. 快照、克隆、模板的区别

| 功能 | 作用 |
| --- | --- |
| 快照 | 记录某一时刻状态，便于回退 |
| 克隆 | 复制出一台新虚拟机 |
| 模板 | 固化标准镜像，便于批量创建 |

- 快照不是长期备份。
- 长时间保留过多快照会影响性能和空间。

#### 4. FC SAN 常见术语

| 术语 | 说明 |
| --- | --- |
| HBA | 主机总线适配器，服务器接入 FC 网络的卡 |
| WWN | FC 世界中的唯一标识 |
| Zoning | 交换机层面访问隔离 |
| LUN | 分配给主机的逻辑磁盘 |
| Multipath | 多路径，提高容错和吞吐 |

#### 5. 运维视角排障思路

1. 虚拟机起不来时，先看宿主资源和数据存储状态。
2. 网络不通时，区分虚拟交换机、VLAN、物理交换机和 IP 配置问题。
3. 存储看不到时，重点查 HBA、WWN、Zoning、LUN 映射、多路径。

### 高频考点

- 桥接、NAT、仅主机模式的区别。
- 快照不是备份。
- HBA、WWN、Zoning、LUN 是 FC SAN 高频术语。
- 虚拟化与 SAN 存储常在同一基础设施题目里出现。


<h2 id="Docker/K8s">Docker/K8s</h2>

### 基础介绍

Docker 代表容器化，Kubernetes 代表容器编排。
容器的核心价值是轻量、标准化、易分发，K8s 的核心价值是大规模管理这些容器。
桌面运维岗位不一定日常维护整套 K8s 集群，但越来越常见的是需要看懂容器运行状态、镜像版本、日志、配置和简单的编排对象。

### 关键知识

#### 1. 容器和虚拟机的区别

| 维度 | 容器 | 虚拟机 |
| --- | --- | --- |
| 内核 | 共享宿主机内核 | 自带完整客户机系统 |
| 启动速度 | 快 | 相对慢 |
| 资源占用 | 更轻 | 更重 |
| 隔离粒度 | 进程级 | 系统级 |

- 这组比较几乎是容器入门必考题。

#### 2. Docker 最核心的四类对象

| 对象 | 说明 |
| --- | --- |
| Image | 镜像，是模板 |
| Container | 容器，是镜像运行实例 |
| Volume | 数据卷，用于持久化 |
| Network | 容器网络 |

#### 3. Docker 常用命令

| 命令 | 作用 |
| --- | --- |
| `docker images` | 查看镜像 |
| `docker ps -a` | 查看容器 |
| `docker logs` | 查看日志 |
| `docker exec -it` | 进入容器 |
| `docker inspect` | 查看详细配置 |

#### 4. K8s 核心对象

| 对象 | 作用 |
| --- | --- |
| Pod | 最小调度单元 |
| Deployment | 管理无状态副本 |
| Service | 提供稳定访问入口 |
| ConfigMap | 普通配置 |
| Secret | 敏感配置 |
| PV/PVC | 持久化存储 |
| Ingress | 入口层路由 |

#### 5. 探针和资源限制

| 配置 | 作用 |
| --- | --- |
| livenessProbe | 判断是否存活 |
| readinessProbe | 判断是否可接流量 |
| CPU/Memory limit | 限制资源上限 |
| request | 资源申请基线 |

#### 6. 运维最常见的排障入口

| 命令 | 作用 |
| --- | --- |
| `kubectl get pods` | 看状态 |
| `kubectl describe pod` | 看事件和调度信息 |
| `kubectl logs` | 看容器日志 |
| `kubectl get svc` | 看服务暴露 |
| `kubectl get events` | 看最近事件 |

#### 7. 常见风险点

- 镜像版本漂移。
- 容器重启循环。
- 配置没更新到 Pod。
- 数据没挂卷导致容器重建后丢失。
- Readiness 没配好导致流量打到未就绪实例。

### 高频考点

- Image、Container、Volume、Network 的角色。
- 容器与虚拟机的对比。
- Pod、Deployment、Service 的关系。
- `docker logs` 和 `kubectl logs` 是高频排障命令。
- 探针和资源限制常作为稍高难度概念题出现。


<h2 id="主机安全">主机安全</h2>

### 基础介绍

主机安全关注的是服务器和终端本身是否处于受控状态。
它不是某一个单独产品，而是一组控制措施：账号、口令、权限、补丁、恶意代码防护、日志审计、端口暴露、数据保护和备份恢复。
桌面运维工程师经常直接面对主机安全，因此这部分内容既适合做考试题，也非常贴近实际工作。

### 关键知识

#### 1. 主机安全的核心目标

| 目标 | 说明 |
| --- | --- |
| 防入侵 | 不让未授权者进来 |
| 防提权 | 不让低权限随意拿到高权限 |
| 防破坏 | 不让恶意程序篡改系统 |
| 防泄露 | 不让敏感数据被带走 |
| 可追溯 | 出事后能查清谁做了什么 |

#### 2. 账号与权限控制

| 动作 | 意义 |
| --- | --- |
| 禁用默认高危账号 | 降低攻击面 |
| 最小权限原则 | 只给必需权限 |
| 强密码与 MFA | 提高账号安全 |
| 定期清理僵尸账号 | 防止离岗账号风险 |

#### 3. 补丁与漏洞管理

- 不打补丁，主机安全就是空中楼阁。
- 补丁管理既要及时，也要考虑业务窗口和验证。
- 补丁策略一般需要“测试验证 -> 分批上线 -> 异常回退”。

#### 4. 杀毒、EDR 与基线加固

| 能力 | 说明 |
| --- | --- |
| 杀毒 | 传统恶意代码检测 |
| EDR | 更强调行为检测与响应 |
| 基线加固 | 规范系统策略和配置 |

#### 5. 端口、服务与暴露面控制

- 不需要的服务应关闭。
- 不需要暴露的端口不应对外开放。
- SSH、RDP、数据库端口等都应结合访问控制和审计。

### 高频考点

- 最小权限原则。
- 补丁管理和恶意代码防护。
- 日志审计与追溯能力。
- 高危端口和默认账号风险。


<h2 id="终端管理">终端管理</h2>

### 基础介绍

终端管理是桌面运维的主战场之一。
它涵盖账号体系、域控、组策略、准入、软件分发、资产盘点、远程协助、桌面虚拟化和统一策略控制。
很多人把桌管理解成“装机和修机”，但成熟的终端管理更像一套企业级治理体系：谁能用、装什么、怎么配、能不能进网、出了问题怎么远程处理。

### 关键知识

#### 1. AD 域控的作用

| 能力 | 说明 |
| --- | --- |
| 统一认证 | 一个账号访问多种资源 |
| 集中管理 | 用户、计算机、组、策略统一控制 |
| 单点登录 | 减少重复认证 |
| 审计留痕 | 更便于统一安全管理 |

#### 2. 常见 AD 术语

| 术语 | 含义 |
| --- | --- |
| 域 | 基本安全边界 |
| 域控制器 DC | 保存目录数据、处理认证 |
| OU | 组织单元，用来分层管理 |
| GPO | 组策略对象 |
| 林 Forest | 更大范围的逻辑组织 |

#### 3. 组策略为什么重要

| 策略方向 | 典型内容 |
| --- | --- |
| 密码策略 | 长度、复杂度、有效期 |
| 桌面策略 | 壁纸、快捷方式、屏保 |
| 软件策略 | 安装、卸载、限制运行 |
| 安全策略 | 审计、端口、设备控制 |

- GPO 是桌面终端批量管理最常见的核心手段。
- 考试里经常把 GPO 和本地安全策略放在一起比较。

#### 4. 准入控制的三步链路

| 环节 | 说明 |
| --- | --- |
| 认证 | 你是谁 |
| 授权 | 你能访问什么 |
| 合规检查 | 你的设备状态是否达标 |

- NAC 题目本质就在这个链条里。
- 不合规终端不能直接进核心网络，是企业内网常见要求。

#### 5. 软件分发与统一管理

| 方向 | 典型动作 |
| --- | --- |
| 软件安装 | 批量安装浏览器、办公软件、安全代理 |
| 补丁更新 | 操作系统和应用统一升级 |
| 策略控制 | 控 USB、控打印、控浏览器设置 |
| 资产盘点 | 设备型号、归属人、位置 |

#### 6. 远程协助与桌面虚拟化

| 模式 | 特点 |
| --- | --- |
| 远程桌面协助 | 适合故障处理 |
| VDI | 桌面集中在服务器侧 |
| IDV | 终端本地运行虚拟桌面 |
| RDS | 多用户共享远程桌面服务 |

#### 7. 终端管理里的常见矛盾

- 安全和易用性的平衡。
- 统一策略和个别部门特殊需求的平衡。
- 用户体验和合规要求的平衡。
- 远程办公与内网安全的平衡。

### 高频考点

- AD、DC、OU、GPO 是基础概念。
- NAC 的认证、授权、合规检查链路。
- 桌面虚拟化与传统终端的区别。
- 终端管理不只是修电脑，更是统一策略、软件分发和资产治理。


<h2 id="Linux/Kylin">Linux/Kylin</h2>

### 基础介绍

Linux/Kylin 是桌面和服务器环境中都非常重要的操作系统知识点。
对桌面运维考试来说，重点不在内核源码，而在目录结构、用户权限、进程服务、日志、网络、磁盘、软件包管理、常见性能和安全命令。
麒麟系统作为国产 Linux 生态代表，也让“会看 Linux”变成很多岗位的基础要求。

### 关键知识

#### 1. 文件系统层级要形成地图感

| 目录 | 作用 |
| --- | --- |
| `/` | 根目录 |
| `/bin` | 常用基础命令 |
| `/sbin` | 系统管理命令 |
| `/etc` | 配置文件 |
| `/var` | 可变数据、日志 |
| `/home` | 普通用户目录 |
| `/root` | root 家目录 |
| `/usr` | 用户程序与资源 |
| `/opt` | 第三方软件目录 |
| `/proc` | 进程和内核信息 |
| `/dev` | 设备文件 |
| `/boot` | 启动相关文件 |

- 目录题是 Linux 章节经典送分题。
- 真正排障时，目录结构也决定你能否快速找到配置和日志。

#### 2. 用户、组与权限体系

| 文件 | 作用 |
| --- | --- |
| `/etc/passwd` | 用户账号信息 |
| `/etc/shadow` | 加密口令信息 |
| `/etc/group` | 组信息 |

| 权限位 | 含义 |
| --- | --- |
| `r` | 读 |
| `w` | 写 |
| `x` | 执行 |

| 数字权限 | 含义 |
| --- | --- |
| 7 | `rwx` |
| 6 | `rw-` |
| 5 | `r-x` |
| 4 | `r--` |

- `chmod 755`、`644` 的数字含义是必考基础。
- 桌面运维工作里，账号和权限问题几乎天天会遇到。

#### 3. 进程、服务与 systemd

| 命令 | 用途 |
| --- | --- |
| `ps -ef` | 查看进程 |
| `top` | 实时看资源 |
| `kill` | 结束进程 |
| `systemctl start/stop/status` | 管理服务 |
| `journalctl -u xxx` | 查看服务日志 |

- Linux 新系统大多以 systemd 为主。
- 所以服务管理和日志查看几乎离不开 `systemctl` 与 `journalctl`。

#### 4. 软件包管理

| 体系 | 常见命令 |
| --- | --- |
| Debian/Ubuntu | `apt`、`dpkg` |
| RHEL/CentOS/Kylin 常见生态 | `yum`、`dnf`、`rpm` |

- 考试喜欢考“安装、卸载、更新”的命令差异。
- 实际工作里，更关键的是懂仓库、依赖和离线安装。

#### 5. 网络基础命令

| 命令 | 用途 |
| --- | --- |
| `ip a` | 查看 IP 和网卡 |
| `ss -tulnp` | 查看端口监听 |
| `ping` | 测连通性 |
| `traceroute` | 看路径 |
| `nslookup` / `dig` | 看 DNS |

- 传统的 `ifconfig`、`netstat` 仍可能见到，但现代系统更推荐 `ip`、`ss`。

#### 6. 日志系统

| 日志 | 常见位置 |
| --- | --- |
| 系统通用日志 | `/var/log/messages` 或 `/var/log/syslog` |
| 认证日志 | `/var/log/secure` 或 `/var/log/auth.log` |
| 内核日志 | `/var/log/kern.log` |
| 审计日志 | `/var/log/audit/audit.log` |

- “出问题先看日志”在 Linux 上是铁律。
- 认证失败、sudo 异常、SSH 登录问题都常从安全日志入手。

#### 7. 磁盘、文件系统与挂载

| 命令 | 用途 |
| --- | --- |
| `df -h` | 看文件系统空间 |
| `du -sh` | 看目录占用 |
| `lsblk` | 看块设备 |
| `mount` | 看挂载 |
| `/etc/fstab` | 开机自动挂载配置 |

- 磁盘满了不一定是数据量大，也可能是日志没轮转、临时文件没清理、挂载异常导致写到根分区。

#### 8. 定时任务与自动化

| 方式 | 用途 |
| --- | --- |
| `cron` | 定时执行脚本 |
| `systemd timer` | 更现代化的任务调度 |

- Linux 系统管理和 Shell 章节是联动的。
- 计划任务题经常和备份、巡检、日志清理一起出。

#### 9. 常见性能分析思路

| 资源 | 常用命令 |
| --- | --- |
| CPU | `top`、`uptime` |
| 内存 | `free -h` |
| 磁盘 I/O | `iostat`、`iotop` |
| 网络 | `ss`、`sar -n DEV` |

- Linux 性能题的核心不是背参数，而是知道“先看哪一类资源”。

#### 10. 安全与加固意识

| 动作 | 价值 |
| --- | --- |
| 关闭无用服务 | 减少攻击面 |
| 限制 root 远程登录 | 降低暴力破解风险 |
| 使用 sudo | 替代长期 root 操作 |
| 配置防火墙 | 限制端口暴露 |
| 审计日志留痕 | 便于追查 |

#### 11. Kylin 语境下的补充理解

- Kylin 本质上仍在 Linux 体系内，很多管理思路和命令共通。
- 但在国产生态项目里，更要关注软件源、兼容包、驱动适配和浏览器插件生态。
- 题目有时不会直接考 Kylin 特有命令，而是把它放到“国产化 Linux 环境”场景题里。

### 高频考点

- 目录结构、用户权限、服务管理是三大基础题。
- `chmod` 数字权限、`systemctl`、`journalctl`、`df`、`du` 是高频命令。
- `ip a` 和 `ss` 是现代系统网络排查常用命令。
- 日志路径和文件作用经常一起考。
- Linux 安全加固通常与 root、sudo、SSH、日志审计、防火墙一起出现。


<h2 id="Windows">Windows</h2>

### 基础介绍

Windows 是桌面终端最常见的操作系统之一，也是桌面运维工程师最熟悉的日常环境。
但考试不会只考你会不会点图形界面，而是会考账号与组、组策略、服务与进程、事件日志、本地安全策略、PowerShell 与远程管理这些偏管理和排障的内容。
真正的能力，是把“界面操作”和“命令行、策略、日志”串成一套体系。

### 关键知识

#### 1. 账号与组管理

| 工具 | 场景 |
| --- | --- |
| 计算机管理 | 图形化查看本地用户和组 |
| `net user` | 创建、删除、改密码 |
| `net localgroup` | 组管理 |

#### 2. 本地策略与组策略

| 工具 | 作用 |
| --- | --- |
| `secpol.msc` | 本地安全策略 |
| `gpedit.msc` | 本地组策略编辑器 |
| 域 GPO | 域环境统一控制 |

- 组策略更适合统一管控。
- 本地策略更适合单机控制。

#### 3. 服务与进程管理

| 工具或命令 | 用途 |
| --- | --- |
| `services.msc` | 看和管服务 |
| `sc` | 命令行管理服务 |
| `tasklist` | 看进程 |
| `taskkill` | 杀进程 |
| PowerShell `Get-Service` | 更灵活的脚本化管理 |

#### 4. 事件日志是排障重点

| 日志类别 | 用途 |
| --- | --- |
| 系统日志 | 驱动、服务、硬件异常 |
| 应用程序日志 | 软件崩溃和兼容问题 |
| 安全日志 | 登录、提权、审计 |
| Setup 日志 | 补丁、安装、升级 |

- Windows 排障常见动作就是“先复现，再去事件查看器查证据”。

#### 5. PowerShell 的价值

- PowerShell 是现代 Windows 运维的核心能力之一。
- 它不是简单替代 CMD，而是更适合做对象化、脚本化管理。
- 会基础 PowerShell，排障效率和批量运维能力会明显提升。

#### 6. 常见风险点

- 本地管理员权限过多。
- 共享目录权限过宽。
- 补丁长期不更新。
- 事件日志不查、只看界面报错。
- 杀毒、EDR、审计策略缺失。

### 高频考点

- `net user`、`net localgroup`、`tasklist`、`taskkill`。
- 组策略与本地安全策略区别。
- 事件查看器的几个核心日志类型。
- PowerShell 与传统图形界面的关系。
- 账号、服务、日志是 Windows 章节高频主线。


<h2 id="服务器基础">服务器基础</h2>

### 基础介绍

服务器基础部分主要解决“看懂硬件、理解部署、知道带外管理和排障逻辑”。
桌面运维岗位虽然不一定长期驻守机房，但很多企业要求桌面运维能够支持基本服务器巡检、硬件识别和异常判断。
这部分内容和网络、虚拟化、存储通常会一起出现。

### 关键知识

#### 1. 基本硬件组成

| 部件 | 说明 |
| --- | --- |
| CPU | 负责计算 |
| 内存 | 负责临时数据存放 |
| 磁盘 | 负责持久化存储 |
| 网卡 | 网络连接 |
| 电源 | 供电，企业机常双电源 |

#### 2. RAID 基础

| RAID | 特点 |
| --- | --- |
| RAID 0 | 高性能，无冗余 |
| RAID 1 | 镜像，冗余好 |
| RAID 5 | 平衡容量与冗余 |
| RAID 10 | 性能和冗余都较好 |

#### 3. 带外管理

| 技术 | 厂商示例 |
| --- | --- |
| iDRAC | Dell |
| iLO | HPE |
| BMC / IPMI | 通用 |

- 带外管理的核心价值是“系统挂了也能看硬件状态”。

#### 4. 基础排障思路

1. 先分硬件问题还是软件问题。
2. 看指示灯、告警、BMC。
3. 看系统日志和服务状态。
4. 看网络、存储、温度、电源等外部条件。

### 高频考点

- CPU、内存、磁盘、网卡、电源的基本角色。
- RAID 基础概念。
- iDRAC、iLO、BMC 是带外管理关键字。
- 排障先分层，不要上来盲目重装。


<h2 id="网络基础">网络基础</h2>

### 基础介绍

网络基础是桌面运维工程师最容易“好像都见过”，但真正做题时最容易混掉的一块。
因为它既有理论模型，又有大量协议和端口，还有很多现场排障命令和链路分析题。
网络部分如果只背端口，很快会乱。
真正有效的方法，是把它拆成五条主线：分层模型、地址与交换、路由与转发、传输层机制、排障方法。

### 关键知识

#### 1. TCP/IP 四层模型

| 层级 | 作用 | 常见协议 |
| --- | --- | --- |
| 应用层 | 提供具体网络服务 | HTTP、HTTPS、DNS、FTP、SMTP、SSH |
| 传输层 | 端到端传输 | TCP、UDP |
| 网络层 | 寻址与路由 | IP、ICMP、ARP |
| 网络接口层 | 帧封装和物理传输 | Ethernet、Wi-Fi |

- 题目常从协议所属层次来考。
- HTTP、DNS、SSH 这些协议本身属于应用层，但会依赖下层 TCP 或 UDP。

#### 2. OSI 七层模型的用途

| 层级 | 典型功能 |
| --- | --- |
| 物理层 | 比特传输 |
| 数据链路层 | 帧和 MAC 地址 |
| 网络层 | IP 路由 |
| 传输层 | TCP/UDP |
| 会话层 | 会话控制 |
| 表示层 | 编码、加密、压缩 |
| 应用层 | 面向用户的网络服务 |

- OSI 更适合做教学与分析模型。
- TCP/IP 更贴近真实网络实现。
- 这两套模型的映射关系是高频题目。

#### 3. IP 地址与子网掩码必须会算思路

| 概念 | 说明 |
| --- | --- |
| IP 地址 | 网络中的逻辑地址 |
| 子网掩码 | 划分网络号和主机号 |
| 默认网关 | 出本网络时转发的下一跳 |
| CIDR | 如 `/24` 这种前缀写法 |

- 很多题会给出 IP 和掩码，让你判断是否同网段。
- 你不一定要手算非常复杂的网段，但至少要对 `/24`、`/16`、`/8` 有直觉。

#### 4. MAC、ARP 与交换机语境

| 概念 | 说明 |
| --- | --- |
| MAC 地址 | 网卡物理地址 |
| ARP | 根据 IP 找 MAC |
| 交换机 | 二层转发设备 |
| VLAN | 二层逻辑隔离 |

- 局域网通信里，IP 只是逻辑地址，最终发帧还是要落到 MAC。
- 所以 IP 通而 MAC 或 ARP 异常，也会导致通信问题。

#### 5. VLAN 与 Trunk

| 概念 | 说明 |
| --- | --- |
| Access 口 | 一般接终端，只属于一个 VLAN |
| Trunk 口 | 承载多个 VLAN 流量 |
| VLAN | 在二层上做逻辑网络隔离 |

- VLAN 题常出在“同网段却互相不通”或“跨 VLAN 需要路由设备”。

#### 6. 路由、NAT 与三层转发

| 概念 | 作用 |
| --- | --- |
| 路由 | 决定数据包走哪条路径 |
| NAT | 地址转换 |
| 默认路由 | 不知道去哪里时的兜底路径 |

- 家庭和办公网络最常见的是 NAT 场景。
- 企业环境里，默认路由配错会导致“本地能通、外网不通”这类故障。

#### 7. TCP 与 UDP 的比较

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接方式 | 面向连接 | 无连接 |
| 可靠性 | 有确认、重传、排序 | 不保证可靠 |
| 开销 | 相对更大 | 更小 |
| 场景 | Web、邮件、文件传输 | DNS、音视频、游戏 |

- 这组对比是网络基础的经典必考题。
- 不是 TCP 一定更“高级”，而是二者适用于不同场景。

#### 8. 三次握手一定要理解目的

| 次序 | 动作 |
| --- | --- |
| 第一次 | 客户端发 SYN |
| 第二次 | 服务端回 SYN+ACK |
| 第三次 | 客户端回 ACK |

- 三次握手的本质是确认双方收发能力都正常。
- 题目爱问“为什么不是两次握手”，核心就在于历史连接和双向能力确认。

#### 9. 四次挥手与 TIME_WAIT

| 步骤 | 动作 |
| --- | --- |
| 第一次 | 主动关闭方发 FIN |
| 第二次 | 对方回 ACK |
| 第三次 | 对方再发 FIN |
| 第四次 | 主动关闭方回 ACK |

- TCP 是全双工，所以双方关闭方向是分开的。
- TIME_WAIT 经常被拿来考“为什么端口占着不立刻释放”。

#### 10. 流量控制与拥塞控制不能混

| 概念 | 关注点 |
| --- | --- |
| 流量控制 | 接收方来得及处理吗 |
| 拥塞控制 | 网络本身会不会被压垮 |

| 拥塞算法 | 含义 |
| --- | --- |
| 慢启动 | 初始时指数增长 |
| 拥塞避免 | 进入平稳增长 |
| 快速重传 | 收到重复 ACK 立刻重传 |
| 快速恢复 | 丢包后快速恢复到稳定状态 |

- 流量控制看窗口。
- 拥塞控制看网络整体状态。
- 这两组词非常容易在题目里混掉。

#### 11. 常见协议与默认端口

| 协议 | 端口 | 说明 |
| --- | --- | --- |
| HTTP | 80 | 明文 Web |
| HTTPS | 443 | 加密 Web |
| SSH | 22 | 远程登录 |
| Telnet | 23 | 明文远程登录 |
| FTP | 21 | 文件传输 |
| SFTP | 22 | 基于 SSH 的文件传输 |
| DNS | 53 | 域名解析 |
| SMTP | 25 / 587 | 发邮件 |
| POP3 | 110 / 995 | 收邮件 |
| IMAP | 143 / 993 | 收邮件 |
| MySQL | 3306 | 数据库 |
| Redis | 6379 | 缓存服务 |
| Oracle | 1521 | 数据库监听 |
| SMB | 445 | 文件共享 |

- 端口题是送分题，但也容易被高频端口混淆。
- 复习时一定要分层记忆，不要只死背数字。

#### 12. DNS、DHCP、NTP 三大基础服务

| 服务 | 作用 |
| --- | --- |
| DNS | 域名转 IP |
| DHCP | 自动分配 IP |
| NTP | 时间同步 |

- 这三个服务看似简单，实际故障率很高。
- DNS 异常会表现为“域名访问不通但 IP 能通”。
- DHCP 异常会表现为“设备拿不到地址”。
- NTP 异常会导致证书、日志、认证链路出问题。

#### 13. HTTP 与 HTTPS 的核心区别

| 项目 | HTTP | HTTPS |
| --- | --- | --- |
| 是否加密 | 否 | 是 |
| 默认端口 | 80 | 443 |
| 证书要求 | 无 | 有 |
| 安全性 | 较低 | 更高 |

- HTTPS 不是“HTTP + 更快”，而是“HTTP + TLS 安全层”。
- 证书、加密、握手、信任链经常一起考。

#### 14. 常见网络排障命令

| 命令 | 平台 | 用途 |
| --- | --- | --- |
| `ping` | 通用 | 测基本连通 |
| `traceroute` / `tracert` | Linux / Windows | 看路径 |
| `nslookup` / `dig` | 通用 | 查 DNS |
| `ipconfig` / `ip a` | Windows / Linux | 查本机地址 |
| `netstat` / `ss` | 通用 / Linux | 查连接和端口 |
| `arp -a` | 通用 | 看 ARP 缓存 |

- 排障顺序一般是：本机配置 -> 网关 -> DNS -> 端口 -> 路径 -> 应用层。

#### 15. 一个非常实用的排障分层思路

1. 先问“是都不通，还是只有某个业务不通”。
2. 再看本机 IP、掩码、网关是否正确。
3. 再 ping 网关和目标 IP。
4. 如果 IP 通域名不通，查 DNS。
5. 如果网络通但业务不通，查端口和服务。
6. 如果端口也通，再看协议层和应用层日志。

#### 16. 安全边界相关网络知识

| 技术 | 作用 |
| --- | --- |
| ACL | 按 IP、端口等控制访问 |
| 防火墙 | 控制流量进出 |
| VPN | 安全远程接入 |
| 反向代理 | 隐藏后端、集中入口 |
| WAF | 防护 Web 攻击 |

- 网络题并不总是纯传输题，也常和安全边界结合。

#### 17. MTU、MSS 与分片意识

- MTU 是一帧能承载的最大传输单元。
- MSS 是 TCP 负载层面可承载的最大报文段大小。
- MTU 配置不当可能引发大包传输异常、VPN 场景性能问题。

#### 18. 邮件、文件共享与数据库协议题怎么记

- 邮件协议记“SMTP 发、POP3/IMAP 收”。
- 文件共享协议记“FTP/SFTP/SMB/NFS”。
- 数据库协议记“数据库名 + 默认端口 + 常见风险”。

#### 19. 常见网络故障现象与联想

| 现象 | 常见方向 |
| --- | --- |
| 能 ping IP 不能访问域名 | DNS 问题 |
| 同网段互不通 | VLAN、ARP、防火墙 |
| 只能访问部分网站 | 路由、DNS、代理 |
| 服务端口不通 | 服务未启动、端口未监听、防火墙阻断 |
| 外网能访问页面但上传失败 | MTU、代理限制、应用限制 |

#### 20. 网络部分与其他章节的联动

- Nginx 题会用到 HTTP/HTTPS、TCP、端口和代理。
- Redis/MySQL/Oracle 题会用到数据库监听端口与网络连通性。
- Windows/Linux 排障题会用到本机 IP、DNS、端口检查。
- 虚拟化和容器题会用到桥接、NAT、VLAN 和服务暴露思路。

### 高频考点

#### 常见概念题

- TCP/IP 四层和 OSI 七层的对应关系。
- TCP 与 UDP 的差异。
- 三次握手、四次挥手的目的。
- 常见协议和默认端口。
- DNS、DHCP、NTP 的职责。

#### 常见比较题

- HTTP 与 HTTPS 的差别。
- 流量控制与拥塞控制的差别。
- Access 口与 Trunk 口的差别。
- 路由与交换的侧重点。
- DNS 异常和纯网络不通的表现差别。

#### 常见场景题

- 域名不通但 IP 通，优先查 DNS。
- 服务访问超时，要同时看网络、端口、应用和代理层。
- 同网段设备不通，不一定是 IP 错，也可能是 VLAN 或 ARP。
- TCP 连接建立失败和应用层报错不是一个层次的问题。
- VPN、HTTPS、证书、时间同步经常会联动出题。

#### 适合做压轴一点的细节题

- 499、502、504 这类状态码如何结合 TCP 和代理链路理解。
- TIME_WAIT 与端口占用的关系。
- 为什么大量终端接入后沟通端口和 DHCP 地址池都要提前规划。
- MTU、MSS 与大文件传输、隧道场景的关联。
- `ping` 能通不代表应用可用，网络层通与应用层通是两个层次。

#### 21. 子网划分的实用速记

| 前缀长度 | 常见掩码 | 可用主机数直觉 |
| --- | --- | --- |
| `/24` | `255.255.255.0` | 约 254 台 |
| `/25` | `255.255.255.128` | 约 126 台 |
| `/26` | `255.255.255.192` | 约 62 台 |
| `/27` | `255.255.255.224` | 约 30 台 |
| `/28` | `255.255.255.240` | 约 14 台 |
| `/29` | `255.255.255.248` | 约 6 台 |

- 终端数量一多，地址规划立刻就和运维管理挂钩。
- 太大的网段会加重广播域压力。
- 太小的网段又会导致频繁扩容和地址不够用。
- 题目有时不会让你硬算二进制，而是用“某网段够不够容纳多少终端”来考你。

#### 22. 常见协议的记忆法不是死背，而是按用途分组

| 分组 | 协议 |
| --- | --- |
| 远程管理 | SSH、RDP、Telnet |
| Web 访问 | HTTP、HTTPS |
| 文件传输 | FTP、SFTP、SMB、NFS |
| 邮件 | SMTP、POP3、IMAP |
| 基础服务 | DNS、DHCP、NTP |
| 数据库 | MySQL、Redis、Oracle |

- 这样记忆比零散背端口更稳。
- 做题时先判断“这是哪一类服务”，再回忆默认端口和风险点。
- 例如 Telnet 最大问题不是端口号，而是明文。
- 例如 SMB 最大问题不是有没有共享，而是权限和暴露范围。

#### 23. 一条从终端到应用的完整排障链路

1. 先确认终端是否拿到正确 IP、掩码、网关和 DNS。
2. 再确认是否能到达网关。
3. 再确认是否能解析域名。
4. 再确认目标端口是否连通。
5. 如果端口通但页面打不开，再看代理层和应用层日志。
6. 如果应用层正常但用户依然报慢，再看链路时延、丢包和服务负载。

- 这条链路特别适合记成答题模板。
- 因为很多网络场景题并不要求你知道厂商命令，而是要求你“排障顺序正确”。

#### 24. 桌面运维视角下最常见的网络题型

- 终端拿不到 IP，先查网口、交换机、VLAN、DHCP。
- 用户访问内网页面报证书错误，先查域名、证书、时间同步、浏览器信任链。
- 打印机能 ping 通但无法打印，可能是端口、驱动、共享或应用协议问题。
- 域控登录慢，不一定只是域控性能问题，也可能是 DNS 或时间同步问题。
- VPN 能连上但业务访问慢，要同时看隧道、路由、DNS 和应用服务质量。

#### 25. 适合作为综合大题的知识联动点

- Nginx 502/504 可以从 TCP、上游端口、服务状态和超时配置一起分析。
- 数据库连接异常可以从应用配置、网络连通、监听端口、认证策略一起分析。
- Windows 域登录问题可以同时涉及 DNS、Kerberos、时间同步和网络可达性。
- 容器服务访问异常可以同时涉及 Pod、Service、Ingress、端口和网络策略。
- 虚拟化环境下的网络故障又可能和 vSwitch、VLAN、物理交换机策略联动。
